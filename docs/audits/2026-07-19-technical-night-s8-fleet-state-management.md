## 2. Designed/intended shape (intake requirements + ruling)

`docs/intake/2026-07-12-siem-requirements-ruled-pack.md` (intake-id 14, status **RULED**, the consolidation of `2026-07-13-siem-fleet-management-requirements.md` [Fable] + `-codex.md` [Codex sol], consumed-by `#328`) is the governing authority; the two `2026-07-13-*` drafts are retained as provenance only.

Directly on-point for S8's question ("does the operator need a SQL/SIEM store"):
- **§5 Non-goals (ruled pack, binding):** *"no Grafana/Loki/ELK-class stack or hosted service (**permanently rejected**)"*; *"no resident daemons/agents/services/queues/brokers"*; *"Platform tripwire: a candidate is a PLATFORM and out if it runs resident, owns state not regenerable from git + JSONL, carries its own upgrade/ops lifecycle, or introduces a rule DSL to learn."*
- Fable draft Non-goals (unioned in, unchanged): *"Full SIEM / log-platform stacks — Grafana, Loki, ELK-class: **PERMANENTLY REJECTED**... Posture stands: **libraries-not-platforms — JSONL events + SQLite/DuckDB-class store + one viewer.**"*
- Fable draft **FR-18 (Could tier, not Must/Should):** *"Derived local read-model. A disposable SQLite/DuckDB-class index built FROM the JSONL when a witnessed query need arrives — rebuildable, never the system of record, no server."* — this is the pack's own answer to S8's exact question, and it is explicitly a *rent-rule, only-when-witnessed-need* item, not a standing requirement.
- **Annex A volumes arithmetic (kept from Fable, "terminal on arithmetic"):** ≤1 MB/day, tens of MB/month uncompressed across an 8-repo fleet — *"three-plus orders of magnitude below any log-platform threshold... independent of the standing doctrinal rejection."*
- **Annex B pattern 7 (store/viewer discipline):** *"Flat files as source of truth; embedded DB as disposable derived index; viewers read, never own"* → *"JSONL = record of truth; SQLite/DuckDB-class only as FR-18 rebuildable index; one local-HTML viewer."*
- **Annex C (PULL ratified §2):** consumer-local gitignored JSONL spools + a hub-owned incremental read-only collector — no shared write target, no hub-address coupling. Reopen tripwires (any one revives the fork → Council): multi-machine fleet, a near-real-time consumer, a hub-unreadable repo, or lag/retry exceeding the survival metric — **none of these are current facts**.

What the pack is actually asking for (§1/§4, the FR-8/FR-9 telemetry spine — five mechanism states, opportunity-denominator, collector self-health, idempotency, FR-A sanctioned-lane queryability, FR-4 ruling-addressability) is a **different problem class than "state too big for YAML"**: it is *did-it-fire* telemetry, not *what's-declared* state. The ruled pack never frames the fleet's declared/parity state itself as a scale problem requiring a database — §7 explicitly leaves *"store/viewer class (SQLite vs DuckDB)"* as a **Phase-A build decision, least-commitment, not settled here.**

## 3. Gap

**What #328 actually delivered vs. the pack's full scope:** `parity-surfaces.yaml` + `fleet_parity.py` cover FR-1/FR-2/FR-3/FR-4/FR-5/FR-6/FR-7(partial via #332)/FR-12 — the *conformance/fidelity/divergence/version* legs (intake questions 1/2/4/5 in the Fable draft's operator-questions list) — and this is **already shipped and already a blocking gate** ([#337], 2026-07-18). The *execution* leg (intake question 3, "did the carried organs actually FIRE") is only built for `fleet_parity`'s own run (its `emit_events()` writes a JSONL line per finding + one run-summary, gitignored `logs/parity-events.jsonl`) — there is **no cross-organ per-fire event log yet**, and grep across `scripts/` finds no `expectation-join`/silence-detection implementation for any other hook/gate. No open BACKLOG ticket currently names FR-8 (general)/FR-9/FR-A/opportunity-denominator/five-state-spine — the telemetry half of the pack is un-ticketed, not merely unbuilt.

Queries that are **genuinely hard today** (witnessed, not hypothetical):
1. **"All dispositions expiring in the next 30 days, fleet-wide"** — `disposition-register.yaml` has a `review_date` field, but only **2 of 14** active entries carry one; `audit.py`'s only consumer of disposition data is the ADR-75 *backward-looking* stale-decoration (`[stale] disposition ... matched no live WARN`, `scripts/audit.py` L2821/L2830) — there is no forward-looking expiry scan. Today: manual `grep review_date` + mental date math. Not hard *because of volume* (14 rows) — hard because **no reporter asks that specific question yet**.
2. **"Which repos are behind on floor hash"** — `check_floor_hash.py` runs per-repo at SessionStart (local, pass/fail only); neither `fleet_health.py` (525 lines, no `floor` reference at all) nor any other script aggregates floor-hash status across the 6 registered repos into one view. A cross-repo answer requires opening each repo.
3. **"Every undeclared divergence across N repos"** — this is **NOT hard today**; it is exactly what `fleet_parity.py` already answers in one run (digest + stdout + now a blocking gate). This item, cited in the assignment brief as a canonical hard query, is already solved by the existing yaml+reporter pattern — worth flagging so the gap isn't overstated.
4. **"Did organ X fire this week, in repo Y"** — hard today for any organ other than `fleet_parity` itself: no event log exists for the other ~30+ pre-commit/session/Stop organs (Annex A's own source inventory: hub ~15 pre-commit + 4-5 SessionStart legs + Stop legs × 6 repos). This is the pack's core FR-8/FR-9 motivator (the witnessed S1 silent-Stop-hook case) and remains open.

**Scale inflection assessment:** none of the *declared-state* surfaces (77 parity rows, 14 dispositions, 116 backlog tasks, 6 repos, 182 index findings) are anywhere near a size where `yaml.safe_load` + Python + grep stops working — these are files a human can `Read` in full in one call, and the existing reporters already do single-pass in-memory joins across all of them in a few seconds (`fleet_parity.py`'s own perf complaint, [#343], is about *pre-commit frequency*, not data volume). The volume argument that *would* eventually matter — JSONL event count once FR-8 telemetry ships broadly (Annex A: "low thousands of events/day worst case... ≤1 MB/day, tens of MB/month") — is explicitly pre-computed in the ruled pack and lands **three-plus orders of magnitude below** the threshold that would justify a database, let alone a SIEM. There is no evidence at current fleet scale (n=6 registered, plan-of-record 5-8+) that a queryable store is needed; the evidence instead shows a **missing-reporter gap** (items 1/2/4 above), not a **data-scale gap**.

## 4. Proposed MECHANISM / RECOMMENDATION

**(a) Stay yaml + git + better reporters — RECOMMENDED for now.** Extend the existing pattern with small, targeted, single-purpose scripts (mirroring `fleet_parity.py`'s own shape) for the specific gaps found in §3: a disposition-expiry scanner (~30-50 lines, reads `disposition-register.yaml`, flags `review_date` within N days) and a fleet-wide floor-hash roll-up (reads each `<repo>/.claude/CLAUDE-FLOOR.md.sha256` sidecar, one summary table). **Cost:** ~0.5-1 build day per query-shape; zero new dependencies (stdlib + PyYAML, already in use); zero maintenance beyond the existing script corpus's normal upkeep. **Layer-2 fit:** exact precedent match — read-only validator, run-to-completion, no state mutation (ADR-28/36).

**(b) A lightweight local queryable read-model (SQLite, built FROM the yaml/JSONL) — DEFER, ready-when-needed.** This is precisely FR-18 in the ruled pack's own Fable draft: a disposable, rebuildable index, never the system of record, no server. Recommend **SQLite over DuckDB** if/when this tier is built: SQLite is Python stdlib (`sqlite3`) — **zero new dependency**, whereas DuckDB would require operator confirmation per the no-new-deps rule (though DuckDB's ability to `SELECT * FROM read_json('logs/*.jsonl')` directly against flat files with no ingest step is a real ergonomic edge if/when the JSONL event volume grows — worth naming as the fallback, not the default). **Trigger to build:** a *witnessed* recurring need for a multi-file join query that a single-purpose reporter can't cleanly answer (the rent rule already governing FR-18/FR-20 in this pack) — not proactively. **Cost:** ~1-3 build days for a first cut (`scripts/build_read_model.py`: ingest all `ecosystem/*.yaml` + any `logs/*.jsonl` into a fresh on-demand SQLite file, never committed, regenerated per run); near-zero ongoing maintenance because it is disposable/regenerable by construction — the exact opposite of typical database-maintenance cost. **Layer-2 fit:** fine as a **read-model reporter** — regenerable from git + yaml/JSONL, mutates nothing upstream, run-to-completion — the same posture already blessed for `index.yaml` (audit.py regenerates it wholesale). It would **violate** Layer-2 the moment it became persistent/resident/authoritative (a service other tools write to, a thing with its own migration/upgrade lifecycle) — that crosses into the pack's own "Platform tripwire" and must not happen without a fresh ruling.

**(c) Full SIEM/SQL store (Grafana/Loki/ELK-class or a standing database service) — REJECTED, do not build.** Already **permanently rejected** by name in the ruled pack (§5) and its Fable-draft non-goals, on arithmetic grounds (Annex A) independent of doctrine. Would also violate the standing hermetization/no-resident-anything posture and Layer-2's "no orchestration scripts... validators only" invariant (ADR-28/36) — a SIEM ingest pipeline is itself an orchestration/service component, not a read-only validator. No cost line is offered because this option is off the table at current or plan-of-record (5-8 repo) scale; the pack's own reopen tripwires (multi-machine fleet, near-real-time consumer, a hub-unreadable repo, lag/retry blowing the survival metric) are the only conditions that would revisit this, and none are current facts.

**Net recommendation:** (a) now, for the two concrete gaps witnessed in §3; (b) shelved and named as the pre-approved next step (zero-new-dep via SQLite) the day a recurring cross-file join need is actually witnessed — do not build it speculatively; (c) stays permanently off the table per the existing ruling. This reconciles cleanly with the ruled pack's own least-commitment posture (§7: *"store/viewer class... Phase A build decisions, not settled here"*) — S8 finds no new evidence that argues for moving off that least-commitment stance sooner.
