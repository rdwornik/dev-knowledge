### F1 [HIGH] `scripts/gen_audit_index.py` — an untracked SYMLINK bypassed the tracked-files filter

**The finding.** `_is_tracked` derived the repo-relative name with `path.resolve()`, which
FOLLOWS a symlink. An untracked `docs/audits/2026-02-02-technical-scratch.md` pointing at a target
outside the repository resolved out of `_REPO_ROOT`, hit the `ValueError` branch, and was
**INCLUDED** — because that branch's deliberate policy is include-on-unknown.

**Why it matters, and why HIGH is right.** This is the *same* defect the commit under review was
written to fix, walking back in through the one door left open. The generated bytes depend on
local scratch state again, and `--check` can red on another checkout of the same commit — which
makes the `audit-index-freshness` gate unholdable, i.e. armed-looking and unusable.

**REPRODUCED** on a real temp git repo before acceptance: committed audit seeded, index rendered,
then an untracked symlink added into `docs/audits/` →
`bytes changed by an UNTRACKED SYMLINK: True`, `scratch row present: True`.

**FIX.** Derive the name **lexically**: resolve the PARENT, keep the entry's own name
(`(path.parent.resolve() / path.name).relative_to(root.resolve())`). A symlinked file now keeps
its lexical repo-relative name and is correctly excluded when untracked. The `ValueError` branch
is RETAINED and still includes, but it now means only what it says — the audits *directory* lies
outside the root (a synthetic/monkeypatched setup) — rather than doubling as a symlink hatch.
Re-run after the fix: `bytes changed: False`, `row present: False`.

**PINNED** by `test_an_untracked_symlink_does_not_change_the_generated_bytes`, which builds a real
git repo and a real out-of-tree symlink, and skips (never silently passes) where symlink creation
is not permitted.

**NOT shared by the twin, checked rather than assumed.** `generate_organ_index._rel` has the same
`path.resolve()` shape, but its `ValueError` fallback returns `path.as_posix()` — an absolute path
that cannot match a tracked name — so it EXCLUDES. The twin lands on the safe side by accident of
its fallback, not by design; this defect is specific to the include-on-unknown policy chosen here.

### F2 [MEDIUM] `scripts/gen_audit_index.py` — `git ls-files` had no bounded failure path

**The finding.** `tracked_files()` failed open for a missing git (`OSError`) and for a non-zero
exit, but the subprocess had **no timeout**. A hung git waits indefinitely instead of returning
`None`.

**Why it matters.** This runs inside a pre-commit gate. An unbounded wait **hangs the commit**
rather than failing it — and a hang is the failure mode an operator cannot distinguish from work.

**FIX.** `timeout=30`, and the handler widened to `(OSError, subprocess.SubprocessError)` so
`TimeoutExpired` lands on the same fail-open answer as every other failure mode. **PINNED** by
`test_tracked_files_fails_open_when_git_times_out`, which asserts the call is bounded at all
before simulating the timeout — a test that would otherwise pass against the unfixed code.

**DECLARED DRIVE-BY: the twin was bounded in the same commit.**
`generate_organ_index.tracked_files` carried the identical unbounded call, in the identical
function, inside the identical pre-commit gate class. Fixing only the file the finding names would
have re-created exactly the RECORDED-ONLY pattern the night-1 audit flagged as this corpus's
systemic failure — a known defect left standing because it was raised against its sibling. Two
lines, declared here and in the commit message rather than slipped in.

- **`_home_matches` implements the stated grammar correctly** — literals exact, `*` exactly one

  determines rendered order. Recorded rather than quietly kept as if it were a fix.
- **The real-git-repo test is correct for ordinary files** but did not cover the symlink case —
