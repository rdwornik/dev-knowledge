# Codemap grounding — per-repo, before any codemap rollout (#79, first half)

**Date:** 2026-06-03
**Author:** Claude Code (read-only on every sibling; writes only into `.dev-knowledge`)
**Purpose:** Resolve the unknown ADR-71 left open and that gates codemap universalization
(#79). For each repo that has — or is expected to have — a codemap, determine two things:
**(1)** is its committed codemap *hand-authored-deliberate* or *stale generator output*,
and **(2)** is its source layout *compatible* with the hub generator (`scripts/codemap/`)?
The answer sizes the codemap close: a small **marker-aware gate** vs. a larger
**generator fix**.

**Contract honored:** READ-ONLY on every sibling (ADR-28 Layer-2, ADR-69 cross-repo
read-only). The hub generator was run with **no `--write`** against each sibling. Nothing
was modified, generated into, or applied in any sibling. The only write is this file.

**Refs:** ADR-71 (codemap layout finding — the split this report resolves), ADR-51
(codemap mandatory M/L; 2026-05-22 amendment defining the generator + the
`not generator-managed` hand-authored escape), BACKLOG #79.

---

## Headline (read this first)

> **The safe universalization is SMALL — a marker-aware freshness gate is not just the
> dominant path, it is the *universal* one.** Every repo that has a codemap already
> **deliberately hand-authors** it (all three carry the `not generator-managed` marker),
> and the one repo without a codemap (`corp-sca`) is S-scale flat-layout that
> **needs none** (it already declares a deliberate text-only override). **No repo is both
> stale AND generator-compatible**, so the "regenerate live + gate" path applies to
> *zero* repos, and **no repo genuinely requires the generator fix.** The generator fix
> is optional future enhancement work, not a blocker.

**One honest caveat** (see "Limitation" below): a marker-aware gate, applied to today's
fleet, actively gates **only the hub**. The children's hand-authored codemaps stay
**human-maintained and un-gated** — exactly the deliberate state they chose. The gate's
job is to *prevent blanket regeneration from destroying the curated diagrams*, not to
catch drift in them. Catching child-codemap drift automatically is the *only* thing the
generator fix would buy — and no repo is asking for it.

---

## Method

- For each sibling: read its `ARCHITECTURE.md` CODEMAP block; record committed
  **node / edge / layer** counts and whether the block carries the
  `not generator-managed` marker.
- Run the hub generator read-only: `py -m scripts.codemap.cli generate <repo> --source-root <root>` (**no `--write`**), once at `--source-root src` and once at the
  inner package root (`src/<pkg>`), since all children nest their package one level under
  `src/`. Record generated node/edge/layer counts and stderr warnings.
- "Layers" = distinct `classDef` layer classes actually assigned to nodes (orphan/cycle
  are anomaly classes, not layers). A generated graph where every node is `:::orphan` has
  **0 layers**.

## Why every codemap repo is INCOMPATIBLE (three compounding reasons)

All three failures stem from the same root: the generator detects packages as
*immediate subdirectories of `--source-root` that contain `__init__.py`*, and matches
import edges on the **first dotted component** of each import name
(`ast_walker.py:44-58`). The fleet's actual layout defeats this three ways at once:

1. **Single-package nesting → wrong nodes.** Every child nests its real package one level
   under `src/` (`src/ai_council/`, `src/corp_ops/`, `src/corp/`). At `--source-root src`
   the generator sees **one** node (the package itself, orphaned). At
   `--source-root src/<pkg>` it sees the sub-packages — but misses the **modules**
   (individual `.py` files), which the generator never emits as nodes. The hand-authored
   codemaps are **module-level** (e.g. ai-council's `cli.py`, `synthesis.py`,
   `models.py` are nodes); the generator only ever draws directory-packages. It
   *structurally cannot reproduce* a module-level curated graph (16 curated nodes incl.
   ~11 modules vs. 2 generated sub-package dirs).
2. **Prefixed imports → 0 edges.** Imports read `from ai_council.x import …` /
   `from corp.x import …`. The first dotted component is the **parent** package
   (`ai_council` / `corp_ops` / `corp`), which is *not* among the bare sub-package node
   names → no edge ever matches. Every node lands orphaned. (This is the exact
   "0 edges" corp-style bug ADR-71 described — now confirmed in **all three**, not just
   corp-monorepo.)
3. **Dotted / absent tach keys → 0 layers.** ai-council and corp-ops have **no
   `tach.toml`** (degraded mode → all nodes `:::orphan`). corp-monorepo *has* one, but
   its keys are dotted (`corp.extractor`, …) and don't match the bare node names
   (`extractor`, …) → 0 layer colors assigned.

The net result in every case: a strictly-worse orphan graph (0 edges, 0 layers) that
would **destroy** a curated, layered, module-level diagram if `--write` were ever run.
That destruction risk is *exactly* why each repo planted the `not generator-managed`
marker — and why blanket regeneration is forbidden.

## Recommended approach — per repo

Mapping each repo onto the four ADR-71 decision buckets:

- **ai-council → marker-aware gate.** Hand-authored-deliberate (marker present),
  INCOMPATIBLE layout. *Never regenerate.* Wire `codemap-freshness` as a marker-aware
  hook that **respects the marker and no-ops** on this block.
- **corp-ops → marker-aware gate.** Same: hand-authored-deliberate, INCOMPATIBLE.
  Marker-aware no-op. (Pre-req noted in ADR-71: corp-ops has no `.pre-commit-config.yaml`
  yet — the framework must be bootstrapped before *any* gate lands; that's rollout
  sequencing, not a codemap decision.)
- **corp-monorepo → marker-aware gate.** The original hand-authored case;
  INCOMPATIBLE (corp-style bug). Marker-aware no-op.
- **corp-sca-time-automation → none.** S-scale (~1.8K LOC, 15 flat modules directly
  under `src/`, no sub-packages). Its `ARCHITECTURE.md` already declares a **deliberate
  text-only codemap override per ADR-51** (no CODEMAP markers by design). The package
  graph the generator produces here is **empty** (no sub-packages to detect). **No
  codemap, no gate** — correct as-is.
- **.dev-knowledge (hub) → keep generator-managed.** The only generator-COMPATIBLE,
  live, dogfooded codemap (source root `scripts/`). Its existing `codemap-freshness`
  pre-commit gate stays active; the marker-aware logic must **not** treat the hub's
  unmarked block as hand-authored.

**No repo falls in the "stale + INCOMPATIBLE + wants generation → generator-fix
decision" bucket.** Every codemap is deliberate, not stale.

---

## The resolution this grounding points to (next step, not done here)

Build a **marker-aware freshness gate** in the hub (small): teach the
`codemap-freshness` check to detect a `not generator-managed` marker inside (or adjacent
to) the CODEMAP block and **skip the regenerate-and-diff** for those blocks — pass
unconditionally, never emit a destructive diff. Unmarked blocks (only the hub today) keep
the current regenerate-live-and-diff behavior. Then per repo, wire `codemap-freshness`
via the ADR-71 hook-source-repo stanza; on the children it is a deliberate no-op that
exists as a *safety net* — if a repo ever drops its marker to opt into generation, the
gate activates.

**The generator fix is explicitly NOT on the critical path.** It would only become
worthwhile if a repo wanted its codemap *live-generated and auto-gated* — which would
require fixing all three coupling issues above (prefixed-import edge matching, dotted
tach-key normalization, and the deeper single-package-nesting + module-granularity gap).
No current repo wants that; all four have made the opposite choice (hand-author or
omit). Defer it.

---

## Limitation (honest enforcement scope)

What the marker-aware gate **does NOT do**: it does **not** catch drift in the children's
hand-authored codemaps. Those stay human-maintained — if `ai-council`'s real import graph
changes, nothing tells the operator the diagram is stale. That is the *pre-existing*
condition ADR-71 flagged ("frozen snapshots that silently drift from their source
trees"), and the marker-aware gate **preserves it deliberately** rather than fixing it.
The gate's sole guarantee is: *blanket regeneration can never silently destroy a curated
diagram.* Automatic child-drift detection is the one capability that the (deferred)
generator fix would add — and the absence of that capability is an accepted trade-off,
matching each repo's deliberate hand-authored choice.

---

## Conclusion

The codemap close is **small**. Build the marker-aware gate in the hub and wire it
fleet-wide; respect the `not generator-managed` marker everywhere it appears (all three
children); leave corp-sca codemap-free; keep the hub generator-managed. **No repo
requires the generator fix** — it is optional future enhancement work, not a blocker for
#79.
