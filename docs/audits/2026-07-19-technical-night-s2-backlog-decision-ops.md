# S2 — Backlog decision-ops: RULED → implemented → closed, and how items actually LEAVE

Night-audit cycle-close · Stream S2 · ADR-101 class `technical`; read-only

## 1. Current mechanism (witnessed, file:line)

**Close path (RULED/done → out of BACKLOG.md):**
- `plugins/tier1-lifecycle/scripts/propose_closures.py` — the ADR-70 Tier-1 Stop-hook detector. Read-only; writes only `logs/PROPOSALS-YYYY-MM-DD.md` (L19-23, L28-32). Two evidence tiers: **STRONG** — a `closes [#N]` commit exists in the window but `#N` is still open in BACKLOG.md (`find_strong`, L129-136); **WEAK** — an open task names a concrete repo-relative file that a no-`closes` commit touched (`find_weak`, L139-157). Never mutates BACKLOG (docstring L4-7, L29).
- `plugins/tier1-lifecycle/scripts/review_closures.py` — the reviewer-side re-verification gate, also read-only (L4-9). `cmd_surface` prints a one-line SessionStart nudge (L246-253); `cmd_plan` re-verifies operator-approved ids against **current** BACKLOG + git state and emits a JSON `{"close":[...],"skip":[...]}` plan (L149-180, L256-273) — an id not currently open, or a STRONG id whose evidence SHA no longer exists, is skipped, never closed.
- `/review-closures` command (`plugins/tier1-lifecycle/commands/review-closures.md`) is the only place BACKLOG.md is actually edited: the agent shows STRONG (bulk-approvable) vs WEAK (must type each `#N`, no bulk-approve) candidates, waits for explicit operator approval, then edits BACKLOG.md using the gate's **exact** returned `line` as `old_string` (steps 2-4, L32-51) — `remove_task()` (`review_closures.py` L183-196) refuses (no-op) if the line isn't unique.
- `backlog-id-on-close` (commit-msg hook, `scripts/check_backlog_commit_msg.py`) — requires a bracketed `[#id]` on any commit that removes a task line (referenced review-closures.md L59).
- `backlog-filing-backpressure` (commit-msg hook, `scripts/check_backlog_filing.py` L34-35/66) — the reciprocal ADD-side gate: BLOCKs a commit introducing a new `[#id]` unless the message carries a `kill-candidates:` line (>=1 existing `#id`, or `none — <reason>`).

## 3. Gap

- **No sanctioned code-level DELETION mechanism exists for BACKLOG tasks, docs, or general files.** The only automated backlog-shrink path is propose_closures.py's evidence-based STRONG/WEAK detector, which finds items that *already have completion evidence in git* — it has no notion of "abandon/supersede/never-implement." An item nobody ever finishes has no automated surfacing path at all; it leaves BACKLOG.md only via a human groom pass.
- **Grooming is confirmed ad-hoc, not a standing routine** — `BACKLOG.md:234`'s "Grooming log" is a hand-maintained prose footer (not machine-generated, no freshness gate on it), listing five historical passes over ~5 weeks (2026-06-12, 06-18, 06-25, 07-08) then jumping straight to "Next quarterly: 2026-10-08." Nothing in `.claude/skills/`, `.claude/commands/`, `.pre-commit-config.yaml`, or `.claude/settings.json` hooks fires a grooming routine — grep across the repo for an executable "groom" cron/skill/hook returns nothing; only the 2026-07-08 `docs/audits/2026-07-08-grooming-worksheet.md` exists, and it is a **manually generated, one-off** decision-support artifact (its own header: "leg (b) of #286," "does not rule anything," no regenerate-on-schedule contract).
- **The one real file/code deletion gate that exists (`scripts/safe_remove.py`) is narrowly scoped and doesn't touch BACKLOG at all.** Its `main()` docstring (L291-295) refuses removing a `scripts/` module while a live external code referrer survives — this is the M1 leg only (BACKLOG #218 tracks the still-deferred M2 path/dotted-module-string and M3 declared-prose legs). It has no relationship to BACKLOG.md task lines, docs, or handoffs.
- **The junkyard effect is witnessed concretely**, not merely alleged: `docs/audits/2026-07-09-deletion-candidates-report.md` is an explicit "propose only — nothing deleted, renamed, or modified" sweep. Of its 7-item ratification queue, only **one** category (3 merged-and-undeleted git branches) was a clean safe-delete; everything else resolved to KEEP-by-design / GATED / TRACKED / operator-periodic-review. Item 5 names it outright: *"3 zero-code-referrer modules… each a runnable CLI/canonical-twin kept by design; the #218 M1 code-ref oracle cannot clear them"* — artifacts that persist specifically **because no mechanism exists to clear them**, not because anyone judged them worth keeping.
- **Even the "close" side is self-flagged as under-performing.** `BACKLOG.md:52` **#277** records the propose_closures.py first live run (2026-07-07) proposed **49 items, 0 valid** — a documented 49:0 signal-to-noise ratio, still open (`[P2][M]`, not yet fixed). So the automated half of the ADR-70 loop that *does* exist is itself unreliable today, while the "file" side's only backpressure is the `kill-candidates:` prose line — satisfiable with `none — <reason>`, which caps nothing about net growth.
- Net: filing is gated (kill-candidates: line, mandatory) and closing-of-evidenced-work is gated (backlog-id-on-close, re-verify plan) — but there is **no gate, detector, or routine on the net delta itself**, and the +42-in-11-days measurement above shows that gap is not hypothetical.

## 4. Proposed MECHANISM (script/hook/gate — never prose)

1. **`scripts/gen_grooming_worksheet.py`** (new read-only generator, Layer-2-safe) — mechanize what the 2026-07-08 grooming-worksheet was produced by hand: per-task `git log -S "[#id]" -- BACKLOG.md` first-seen/last-touch ages (the exact heuristic already prototyped in `docs/audits/2026-07-08-grooming-worksheet.md` L16-24), emitting `active` / `aged — review` / `superseded-candidate` classifications. Wire it as a **new `audit.py` check** (`check_backlog_grooming_cadence`) that WARNs when either (a) live task count exceeds the last-recorded groom baseline (currently 74 @ 2026-07-08, read from the `BACKLOG.md` footer) by a threshold (e.g. >50%), or (b) the footer's "Next quarterly:" date has passed with no new "Grooming log" entry — the same regen-and-diff pattern as `gen_audit_index.py --check`, giving `#348`'s "grooming as a standing routine, not ad-hoc" a concrete enforcement site instead of waiting on the full `#270`/`#271` nightly layer.
2. **Point `#347`'s safe-deletion Done-when at `#218`'s M2/M3 legs** as the actual sanctioned mechanism, rather than leaving "ruled or recorded permanent-defer" open-ended: extend `scripts/safe_remove.py` past its current M1-only (`scripts/` code referrers) to M2 (path/dotted-module string refs) and M3 (declared-prose reverse-deps) per `#218`'s existing Done-when — that gate, generalized, **is** the "proof-then-delete" mechanism #347 asks for; today #347 and #218 both exist without one naming the other as its build leg.
3. **A `backlog-net-delta` WARN leg** inside `check_backlog_filing.py` (or a sibling `audit.py` check) that reads the same footer baseline as (1) and prints the running net (filed − closed since last groom) on every commit that adds an id — turning the +42/11-days finding in §1 from a manual night-audit computation into a number the operator sees continuously, closing the loop the `kill-candidates:` line only half-closes today (it forces a *reason*, never a *count*).
