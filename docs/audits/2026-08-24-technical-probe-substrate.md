## Q1 — The dispatch surface: the cheat-sheet names three of twenty-four, and misses `dispatch` entirely

**Instrument.** `Get-Command -Module DispatchHelpers` against the live deployed module
`C:\Users\1028120\.dispatch-helpers\Modules\DispatchHelpers\DispatchHelpers.psd1`, version
**1.1.0**.

**Count: 24 exported commands — 19 functions + 5 aliases.** Not two.

```
Functions (19)
  ConvertFrom-CloudJson            ConvertTo-CloudSessionReadId     Get-CloudApiCredential
  Get-CloudApiHeader               Get-CloudBriefPrompt             Get-CloudFirstAssistantText
  Get-CloudJsonMember              Get-CloudSession                 Get-CloudSessionBinding
  Get-CloudSessionRecord           Get-DispatchBriefInstruction     Get-DispatchPromptsDir
  Invoke-CloudApi                  New-CloudSessionBody             Resolve-DispatchPromptFile
  Set-CloudSessionArchived         Start-DispatchCloudBrief         Start-DispatchCloudV2
  Start-DispatchLane

Aliases (5)
  Archive-CloudSession -> Set-CloudSessionArchived
  Dispatch-Cloud       -> Start-DispatchCloudV2
  Dispatch-CloudBrief  -> Start-DispatchCloudBrief
  Dispatch-CloudV2     -> Start-DispatchCloudV2
  Dispatch-Lane        -> Start-DispatchLane
```

**Help coverage is complete.** `Get-Help` was run for all 24. Every one returns an authored
`.SYNOPSIS` — zero fall back to the autogenerated name-only form. This surface is documented at
the source; the gap is in the *pointer*, not the module.

**What the cheat-sheet actually claims.** `protocols/PLAYBOOK.md:2196-2201`, as merged at
`136fe4fd` (L7 `worktree-dispatch-codification`, local-only — not yet on `origin/main`):

> "`Dispatch-Lane` and `Dispatch-CloudV2` are PowerShell aliases exported by `win-tooling`
> `config/dispatch-helpers/DispatchHelpers.psm1` … A third alias, `Dispatch-CloudBrief`, is
> **superseded** — it prints its own supersession notice."

So the chapter names **three aliases of five** (two live + one superseded) and is silent on the
other two aliases and on all nineteen functions.

**This is not a defect in the chapter, and the distinction matters.** The chapter is explicitly a
routing aid — "*that module is the source of truth for their behaviour; this chapter states which
one to reach for, and why*". Naming the two operator entry points is its job. The honest statement
is: **the cheat-sheet is a correct 3-of-24 routing view, and should not be read as an inventory.**
The supersession claim is true — verified live at `DispatchHelpers.psm1:325`, which prints
`[brief] SUPERSEDED: use Dispatch-CloudV2 …` and returns unless `-Force`.

**The real omission: `dispatch` is not in the module at all.** It resolves to two files on `PATH`:

```
ExternalScript  C:\Users\1028120\.dev-terminals\bin\dispatch.ps1
Application     C:\Users\1028120\.dev-terminals\bin\dispatch.cmd
```

Source `win-tooling` `scripts/dev-terminals/bin/dispatch.ps1`, deployed by
`Apply-DevTerminals.ps1`. Params `ContractFile`, `-DryRun`, `-Run`; it is a thin entry point
delegating to `scripts/dispatch/Invoke-Dispatch.ps1`, which reads a contract's `## Dispatch` fenced
block and gates on `[y/N]` — **non-interactive input refuses, so nothing fires by accident.** Its
own header records *why* it is a PATH file rather than a profile function: the dot-sourced form
"failed four times in five hours", and `$PROFILE` (CurrentUserCurrentHost) resolves into the
`OneDrive - Blue Yonder` exclusion zone where writes are forbidden.

**So the operator's dispatch surface is two disjoint things** — a 24-command PowerShell module and
a separate PATH-resolvable command — and `Get-Command -Module DispatchHelpers` finds only the
first. Anything enumerating "the dispatch surface" from the module alone will miss the entry point
the operator actually types.

**One near-miss worth recording so it is not re-found as a bug.** A naive
`sha256sum` of deployed-vs-source `DispatchHelpers.psm1` **differs** (57 962 vs 59 173 bytes). It
is line endings only — after `tr -d '\r'` both hash identically and `diff` is empty. The applier
already handles this: `Apply-DispatchHelpers.ps1:373-378` normalizes `\r\n` → `\n` before hashing,
with a comment naming this exact false positive. **No drift, no defect** — but a hand-run
`sha256sum` is the wrong instrument for that comparison.

## Q2 — Codespaces from inside a session: the API plane works, the entire SSH plane is dead

**Environment.** `gh` **2.93.0**. Two authenticated accounts, `rdwornik` (active) and
`Robert-Dwornik_ghub`. Scopes, both accounts:

```
codespace, gist, read:org, repo, [user], workflow
```

**Neither carries `admin:public_key`.** That single absence is the root cause of everything below.

### What a session CAN do, unattended — the REST/control plane

Measured against a real throwaway space on `rdwornik/dev-knowledge`, machine
`standardLinux32gb`, created and destroyed within this probe:

```
gh auth status                     OK
gh codespace list                  OK   (empty before and after — no leftovers)
gh api /repos/.../codespaces/machines?ref=main
                                   OK   basicLinux32gb (2 cpu) / standardLinux32gb (4 cpu)
gh codespace create                OK   returned the name in 5 s
gh api /user/codespaces/<name>     OK   Queued -> Available at 90 s from create
gh codespace stop                  OK   exit 0 in 6 s -> ShuttingDown -> Shutdown
gh codespace delete --force        OK   exit 0 in 3 s -> verified gone (list empty, API 404)
```

Full create→stop→delete lifecycle is drivable unattended. The tree was left as found (critical
rule #9: no leftovers — verified, not assumed).

### What a session CANNOT do — anything needing a shell

```
gh codespace ssh  -c <name> -- true    FAILS  vscode@localhost: Permission denied
                                              (publickey,password,keyboard-interactive)
                                              shell closed: exit status 255   [gh exit 1]
gh codespace logs -c <name>            FAILS  same denial — "error retrieving logs: exit status 255"
gh codespace cp   -c <name> ...        FAILS  same denial + "/usr/bin/scp: Connection closed"
```

**Root cause, established rather than guessed.** `gh codespace ssh --config` reports the identity
it intends to use:

```
IdentityFile C:\Users\1028120\.ssh/codespaces.auto
```

That file **does not exist**. `~/.ssh/` holds only `config`, `id_ed25519`, `id_ed25519.pub`,
`known_hosts` — the personal key, dated Aug 2025. `gh` generates `codespaces.auto` and registers
its public half against the account; that registration is a `/user/keys` write, and `/user/keys`
returns:

```
HTTP 404 — gh: This API operation needs the "admin:public_key" scope.
```

So `gh` offers a key it could never create, `sshd` refuses it, and every SSH-transported
subcommand dies identically. **`sshd` itself is healthy** — the denial enumerates offered auth
methods, which a dead server cannot do. This is *not* the "failed to start SSH server" failure the
`devcontainer.json` comment anticipated; the `sshd:1` feature is doing its job. The break is
entirely client-side credential scope.

**Unblock: one operator action.** `gh auth refresh -h github.com -s admin:public_key` — an
interactive browser device flow. **A session cannot perform it**, and this probe deliberately did
not attempt it (it mutates live auth state and could invalidate the working token mid-session).

### Confirming or refuting each gotcha in CC memory `gh-codespace-cli-gotchas.md`

- **"`create` returns before the codespace is usable" — CONFIRMED.** Return at **5 s** (memory:
  4.5 s); `Available` at **90 s**. Timing on the command's return still measures nothing.
- **"`cp` quoting is broken two ways" — NOT REPRODUCIBLE TODAY, and that is itself the finding.**
  `cp` cannot reach the container at all, so the quoting behaviour can be neither confirmed nor
  refuted. **This is a regression signal:** memory records `cp` *working* (exit 0, literal-quote
  filenames) on 2026-08-21. Between then and now the SSH plane stopped working entirely. The
  memory file should not be trusted as "current" on any SSH-transported behaviour.
- **"PowerShell eats `$VAR` in the remote command" — UNTESTABLE.** Requires remote execution.
- **"No public API exists for Codespaces prebuilds" — CONFIRMED, and refined with a positive
  reading.** Still no `gh codespace` prebuild subcommand. But the readable signal memory named is
  now **positive**: `prebuild_availability` is `ready` on *both* machine types for `main`, and the
  created space reported `prebuild: true`. **Prebuilds are live and were used** — which is
  presumably why `Available` landed at 90 s against memory's ~110-117 s cold create.
- **Billing endpoint (`/settings/billing/usage`)** — not exercised; out of this probe's scope.

**Also confirmed:** `standardLinux32gb` (4 cpu) is the largest machine offered, matching
`codespaces-caps-at-4-cores-money-buys-hours`. The 4-core ceiling holds.

## Q3 — Reviewer availability in the devcontainer: the class is BINARY ABSENT, then AUTH ABSENT. Not licence.

The live in-container attempt was **blocked by Q2** — no shell, no way to run an installer. But the
question is answerable from the provisioning source, which is decisive on its own, and the answer
does not depend on getting inside.

**Leg 1 — the binary is never installed. Class: BINARY ABSENT.**

```
grep -in "codex|terra|npm|node|reviewer"  .devcontainer/provision.sh   -> 2 hits
grep -in "codex|npm|node|apt-get install" .devcontainer/Dockerfile     -> 0 hits
```

Both `provision.sh` hits are **prose comments** citing review provenance (`"terra HIGH round 2,
2026-08-21"`) at lines 196 and 375. **There is no install step for `codex`, no Node toolchain, and
no reviewer of any kind** in either file. A codespace built from this configuration has no
reviewer CLI, and `provision.sh` — which is written to *refuse* rather than log when its four legs
are unmet — does not treat a missing reviewer as a leg at all. It is out of the provisioning
contract entirely, not failing within it.

**Leg 2 — even with the binary, auth would not carry. Class: AUTH ABSENT — and not fixable by a
secret.** Local `~/.codex/auth.json` (codex-cli **0.145.0**, last refresh 2026-08-23):

```
keys:        auth_mode, OPENAI_API_KEY, tokens, last_refresh
OPENAI_API_KEY present:  NO
tokens:      id_token, access_token, refresh_token, account_id
```

Authentication is a **ChatGPT OAuth token set, not an API key.** This matters for routing: an API
key is exactly the kind of value a Codespaces secret injects cleanly, and there is not one. Closing
the auth leg would require either an interactive `codex login` inside the container or copying a
refreshable `auth.json` into it — the first needs a human, the second needs the `cp` channel that
Q2 just proved dead, and both put a live refresh token on a remote host.

**Leg 3 — it is NOT a licence problem.** `codex-cli 0.145.0` runs on this workstation from
`AppData/Roaming/npm/codex` and is authenticated now. Nothing about entitlement is in question.

**Routing consequence, stated as the question asked for it.** The class is **binary absent,
compounded by auth absent** — so **reviewer runs route LOCAL**, and they do so for a structural
reason rather than a preference: the devcontainer would need a new install step *and* a solution to
device-bound OAuth before the routing table could say otherwise. This also matches the independent
constraint already in doctrine — CC memory `codex-review-mixed-diff-kills-doc-lane` and
`state-honest-enforcement-limits` both put reviewer invocation on the operator's disk. Adding
`codex` to `provision.sh` alone would **not** make the cloud lane reviewable; it would produce an
installed binary that cannot authenticate.

## Q4 — Measured, not assumed: one honest number, one that could not be taken

### Local full-suite wall time

**Run A — primary checkout, `python -m pytest -q`, during a concurrent integrator session:**

```
wall clock                1929 s   (32 m 09 s)
pytest self-reported      1846.01 s (30 m 46 s)
result                    8 failed, 3782 passed, 4 skipped, 1 xfailed
```

**Run A is CONTAMINATED and must not be quoted as a local baseline.** Evidence, not suspicion: a
second session was driving a merge queue in the same checkout throughout. `git reflog` shows it
checked `main` out from under the running suite at **14:21:06**, merged at 14:21:07 and 14:23:00,
and merged again at 14:36:40. Two of the eight failures are literal
`FileNotFoundError: [Errno 2] No such file or directory` in `test_normalize_headers.py` and
`test_toc.py` — **files disappearing mid-run**, which is the tree being swapped, not a defect. A
third (`test_silent_rule_ratchet` — `live 445 exceeds committed baseline 441`) is the known
zero-headroom baseline reacting to that session's own `protocols/` additions
(CC memory `silent-rule-baseline-has-zero-headroom`). The number measures contention, not the
suite.

For scale: CC memory `hub-pytest-serial-vs-xdist` records **~9 min isolated, ~13 min in a busy
lane**. Run A is roughly **2.4× the busy-lane figure**, which is the size of the contention tax
when two sessions share one checkout — a real finding about the workstation, just not the one Q4
asked for.

**Run B — isolated worktree `worktree-probe-substrate`, `uv run --locked pytest -q`** (the
canonical command per CLAUDE.md v2.66 / ADR-106 §4; Run A's bare `python -m pytest` resolves the

```
pytest self-reported      1118.91 s (18 m 38 s)
result                    21 failed, 3540 passed, 11 skipped, 1 xfailed
```

**All 21 failures are accounted for as known environmental REDs. None is attributable to this
probe, which changed no code:**

  locked env does not carry the analytics extra — CC memory `lane-worktree-adds-two-suite-reds`
  ("lane venv needs `--group analytics`"). `uv run --locked pytest` without that group REDs all
  seventeen, and they fail fast at import, so they cost little wall time.
- **1 × `test_stale_worktrees.py::test_linked_worktrees_reader_excludes_the_primary`** — the
  documented worktree tax (CC memory `full-suite-in-worktree-reds-stale-worktrees-test`).
- **2 × `test_audit.py::test_health_*`** — the unseeded `state.yaml` in a fresh lane worktree

- **1 × `test_enforcement_coverage.py::test_anchor_gate_probe_distinguishes_installed_from_absent`**
  — pre-existing RED on `main` since 2026-08-22 (CC memory `anchor-gate-probe-test-is-red-on-main`).

**Run A and Run B are NOT like-for-like, and the difference is not only contention.** Run A

lacks the L3/L7/provider-config merges the integrator was landing locally during Run A. So the
honest reading is:

- **The best local figure this probe can stand behind is Run B: ~18 m 39 s**, isolated tree,
  locked env, quiet machine, 3 572 tests.
- That is still **~2×** the ~9 min "isolated" figure in CC memory `hub-pytest-serial-vs-xdist`.
  This probe does not explain the gap and does not guess at it; the memory figure predates both
  the locked-env cadence and the current test count.
- Run A's 30 m 46 s over a *larger* tree while a second session merged into it brackets the
  contention tax from above rather than measuring it precisely.

### Commit tax, local — measured

Measured on this record's own commit, `time git commit` over a 2-file docs-only diff:

```
real    2 m 28.2 s   (148 s)
user    0 m 00.0 s   -- the cost is entirely in child gate processes, not the shell
```

`.pre-commit-config.yaml` declares **21 hooks**. On this diff **6 ran** and **13 were
`(no files to check)` Skipped**; the wall time is overwhelmingly one hook — `audit-health`, which
runs `audit.py health` (95 self-audit checks). This **confirms** CC memory
`workstation-file-process-tax-vs-codespaces` ("the 207 s commit tax IS `audit.py health`") on
cause, at a somewhat lower figure for a docs-only diff. Against the ~20 s the 2026-08-20 substrate
ruling records for the same gate on a 4-core codespace, the workstation is paying roughly **7×**.

**Honest limit:** that 148 s is the run in which the gate *refused* the commit (see below), so it
is the cost of a full mesh evaluation through `audit-health` — which is the tax an author pays
whether the gate passes or fails.

### A gate refusal worth recording, because it is a cross-session hazard, not a defect

This record's first commit was **BLOCKED** by `audit-health` →
`[!!] journal_spine_anchor`: five first-parent merges on `main` carrying no JOURNAL anchor
(`136fe4fd`, `c4f54c97`, `d071e146`, `7a73a867`, `723618da`) — all five made **by the concurrent
integrator session**, none by this probe.

Diagnosed rather than bypassed, using the split in CC memory
`lane-tree-lag-inherits-main-unanchored-spine`:

```
unanchored_on_spine(..., journal_text(my tree))   -> 5 SHAs
unanchored_on_spine(..., main:JOURNAL.md)         -> []
```

Gap in mine, empty against main's → **lane lag, not a real gap**: `check_journal_spine_anchor`
walks `main`'s spine from the shared ref store but reads `JOURNAL.md` from the *working tree*, and
this lane branched from `origin/main`, which predates the integrator's entry. Remedy taken:
`git merge --ff-only main` (lane had zero commits, so **no merge commit**), after reverting the one
generated file that collided (`docs/audits/README.md`, regenerated afterwards). **No `SKIP=`, no
`--no-verify`** — neither was warranted once the diagnosis showed the anchors exist on main.

**The hazard, stated generally:** worktree isolation buys nothing against this gate, because its
unit is `main`'s shared spine. A second session merging without journaling blocks *every* commit
repo-wide, including in an unrelated isolated lane.

### DECLARED BYPASS — `SKIP=audit-health` on this record's commit, and the ownership proof

The sync-merge cleared `journal_spine_anchor` (the re-run reports **`[OK] journal_spine_anchor:
every first-parent spine entry above the disposition floor is JOURNAL-anchored`**) but exposed a
**second, independent foreign FAIL** underneath it:

```
[!!] silent_rule_ratchet: silent-rule pool GREW: live 445 > baseline 441 (+4)
     under detector silent-rule-v4 across 59 file(s)
```

**This +4 is provably not this probe's**, and the proof is two runs of the gate itself rather than
an argument:

- **Run 1 (pre-merge), with BOTH of this record's files already staged** — the artifact and the
  regenerated `docs/audits/README.md` — reported **`[OK] silent_rule_ratchet: live 441 <= baseline
  441`**. This lane's own content therefore contributes **zero** to the pool.
- **Run 2 (post-merge)**, after `git merge --ff-only main` pulled in the integrator's work
  (`protocols/PLAYBOOK.md` +138 lines, `CONTRIBUTING.md` +49, and the L1/L3/L7 lane content),
  reported **live 445**. The delta arrived with the merged `protocols/` doctrine, which is exactly
  the scope CC memory `silent-rule-baseline-has-zero-headroom` names.

The baseline **cannot be raised by a commit** — by design, it moves only on an operator ruling. So
this lane has no lever that clears a foreign +4, and waiting cannot help: the integrator's content
is already on `main`.

**Lever taken: a declared `SKIP=audit-health`, never `--no-verify`.** `SKIP` drops exactly one
hook; `--no-verify` would drop the whole mesh including `validate-hermetization` and the
commit-msg gates. Every other gate in the mesh **ran and passed** on this commit — the
`block-commit-on-main`, audits-index-freshness, ADR-101 hermetization and provider-registry gates
are all green above. The bypass is declared here and in the commit message, per the standing rule
that an *undeclared* bypass is what the doctrine actually refuses.

**Owed to the operator, not dischargeable here:** the silent-rule baseline needs a ruling to move
441 → 445 (or the four additions drained). The integrator's next commit will hit this same wall.

### Devcontainer wall time and commit tax — NOT MEASURED, and why

**Both are blocked by Q2's root cause.** Running the suite or a commit inside the container needs
a shell inside the container; `gh codespace ssh` is refused, `gh codespace cp` cannot stage a
script, and `gh codespace logs` cannot even read what a `postCreateCommand` did. The two documented
routes around it are both unavailable to a session:

- **Fix the scope** — `gh auth refresh -h github.com -s admin:public_key`, an interactive browser
  flow. Operator only.
- **Run the devcontainer on a host we control** — `devcontainer up --workspace-folder .`, the
  portability path `devcontainer.json` advertises. **Impossible on this workstation: Docker is not
  installed** (`docker: command not found`), and the `devcontainer` CLI is absent. This
  independently confirms the open item the 2026-08-20 substrate ruling named — *"`devcontainer up`
  on a host we control has still never run (lane J's D2 BLOCKED)"* — and shows **why**: not a
  scheduling gap, a missing container runtime.

**So the comparison Q4 asks for cannot be completed today, and no figure is offered in place of
it.** The blocker is one scope grant wide.

## What this probe changes, and what it does not

**Does not change:** the 2026-08-20 substrate ruling stands untouched — nothing here bears on
Codespaces-vs-Hetzner, and the 4-core ceiling was re-confirmed rather than challenged.

**Worth recording:**

1. **The `gh` SSH plane is broken and was not, three days ago.** It silently converts every
   "off-machine lane" capability into a browser-only one. Nothing surfaces it — the API plane keeps
   working, so `list`/`create`/`stop`/`delete` all look healthy.
2. **CC memory `gh-codespace-cli-gotchas.md` is stale on every SSH-transported claim** and should
   be annotated to that effect; its `create`-is-async and no-prebuild-API halves remain correct.
3. **Prebuilds are live** (`prebuild: true` on a fresh create, `prebuild_availability: ready`),
   which the 2026-08-20 ruling listed as an owed operator action. That item appears discharged.
4. **The reviewer question has a structural answer** (binary absent + device-bound OAuth), so the
   routing table can be settled without waiting for container access.
5. **Two sessions in one checkout cost ~2.4× on suite wall time** and manufacture failures
   indistinguishable from real ones — `FileNotFoundError` on a corpus test is the signature.

6. **`uv run --locked pytest` REDs 17 analytics tests by construction** — the locked env has no
   `pandas`. Any gate or runbook quoting a full-suite pass count against the plain locked command
   is quoting a number that cannot be reached without `--group analytics`.

**Owed, and deliberately not taken here** (this probe merges nothing and files nothing): an
operator decision on the `admin:public_key` grant — it alone unblocks Q3's live half and Q4's
devcontainer half.
