## 1. The loop this maps onto

## 2. Method — and where the method is weak (read before trusting a row)

- **Organs first.** The organ roster is the file-purpose graph (`file_purpose_graph.py why` / `list`, built once and rendered with the organ's own renderer for all 3,010 nodes), the orphan census and process list (`graph_queries.py`, including its `ORPHAN_DISPOSITIONS` register of 40 ruled no-trigger scripts), the pre-commit config read as YAML, and `harness.yaml`. `organ-index.md` was **not** used for arming: it marks every hook ARMED regardless of `stages:` (`to-browser/STATE-OF-THE-HARNESS-2026-09-20.md` §2 — on the operator transport, not in this repo).
- **Triggers are mechanical.** A script's trigger is read from its graph consumer lines (`is triggered by ... [wiring]`, `is imported by ... [wiring]`); a hook's ARMED/INERT is read from the hook's own `stages:`. Where the graph has no wiring edge the row says `GRAPH-GAP` and quotes what `git grep -F <name>` finds, or the orphan-census disposition.
- **Stages and verdicts are a judgement made from each organ's own docstring**, not a graph output. The graph carries no stage. The curated part is a fixed map in one place (the organs whose loop role is stated in their own docstring); everything else defaults to `none`/KEEP, or 15 when a pre-commit hook runs it (16 for pre-push). The verdict column was then reviewed against the code by a separate reviewer (step 5) — see §8.
- **Tables for `.claude/`, the workflows and Ch8 came from Haiku subagents** (one per surface) and were then corrected: ten stage/verdict overrides on `.claude/` rows, `RETIRE-CANDIDATE` withdrawn on the eight disabled SessionStart hooks (they are disabled by ruling with a dated decision, not abandoned), and a `CORRECTION` clause appended to every Ch8 row that said dispatch lives only in `win-tooling`. The three `scripts/` shards Haiku produced were **discarded**: they printed stage `?`, mapped `arm_hooks.py` to stage 1, and treated a `task-implements` edge as a "trigger" (a task row that implements a script is not something that runs it). Two of those agents also left scratch scripts in the worktree root; both were untracked and were removed.
- **Ch8 has 33 procedure rows, not the 44 its author reported.** The count is of table rows in the file.

## 4. Stages 13-16 — what exists, and the concrete missing piece (Done-contract 2)

**Stage 13 RUN — organs exist for the plan, the cap and the guards; the adapter does not exist.**
- Fills it today: `scripts/dispatch.py` (`plan` turns a contract into argv, env delta and model/effort **from the contract**; `govern` binds one lane by session id, polls its usage, and stops it past an enforced cap; `codespace_plan`; `meter_lines` for stream-metered lanes), `templates/dispatch-shim.ps1` (the caller-side spawn — dispatch.py never spawns), `lane_boot.py` (the six `/lane-boot` refusals, including a **GO artifact** the lane must be named in — `check_go_artifact`, `[#685]`), `single_flight.py`, `seat_refusals.py`, `lane_cost.py`, `worktree_seed.py`.
- Probes: **B1** — one SDK process carried a Python hook that fired and denied on every call and a budget that ended the run and reported its cost (adapter-shaped), but the budget overshoots, `query()` raises after yielding its result, and process teardown, cancellation, crash recovery and durable run identity were **not** probed. **B2** — `codex exec` works as a subprocess but returns tokens only: no cost, no model id, no cap, no hook seam. **B4** — a `--bg` spawn from inside a session gets its own row and record.
- **Missing, concretely:** (1) the seam itself — one callable `run(contract, provider) -> {result, usage, cost, model_id, stop_reason}`. Nothing in the repo has that shape: `dispatch.py` returns a plan and hands spawning to PowerShell; its own docstring says stream-metered lanes (codex, `claude -p`) "have the metering primitive here but NO caller-side spawner yet — the shim refuses them". The SDK and codex paths exist only as B1/B2 scratch. (2) `harness.yaml` stage 11 is `command: null`, so `govern` is not reachable from the spine. (3) The **Layer-2 boundary**: CLAUDE.md §5 rule 4 ("no script drives state in a child repo") is why dispatch.py plans and a caller-side shim spawns; a stage 13 that spawns from `dodo.py` must be scoped to the repo the spine runs in, or go through the shim. That is an ADR decision (see the draft ADR), not something this lane decides. **AM-5 (PLAYBOOK :2815-2823) also stands** — "batch lanes are dispatched by the operator via `dispatch <contract>` from a terminal, never spawned from the primary session or any other session". B4 re-witnessed AM-5's premise false a third time, and DECLARE R7 says that re-rules nothing: a session-side stage 13 is barred until the seat re-rules AM-5.

**Stage 14 REVIEW — the pieces exist; nothing is a callable, tracked, structured step.**
- Fills it today: `~/.claude/bin/codex-review.ps1` and the user-level `/codex-review` (both **L0, outside this repo**; the wrapper runs `codex exec --output-last-message` and writes a `docs/audits/*-codex-*.md` file), `review_packet.py` (pre-assembled review inputs, refuses to abbreviate), the routing table's `reviewer` role (`codex`, `gpt-5.6-terra`) checked by `routing_agreement.py` (spine stage 8) and resolved by `provider_router.py`, the `.github/workflows/conductor.yml` `terra` job (**declared, UNARMED — no provider credential in Actions secrets**), and the HANDBACK line grammar (`review=codex HIGH:n ...`) that `audit.py handback` reads at merge.
- **Missing, concretely:** (1) a repo-tracked review step a stage can cite by path — the wrapper lives at L0 and is PowerShell, so a spine stage cannot name it the way stages 1-12 name their scripts; (2) a structured verdict — today the record is a prose audit file whose tally is regex-read; (3) provider independence provable from output — B2 showed `codex exec` reports no model id, so "the reviewer was not the producer's model" cannot be witnessed from the run itself; (4) the CI leg needs a credential — an operator act (conductor.yml states it as two acts).

**Stage 15 GATES — the most complete of the four; what is missing is composition and a trigger, not a gate.**
- Fills it today: `audit.py ship-gate` (every check runs; FAIL or undispositioned WARN blocks) and `audit.py health`, `impacted_tests.py select` / `guard`, ruff, the `verify` skill (pytest + ruff + git-status cadence), the **36 pre-commit hooks — 17 ARMED (12 at commit, 3 at commit-msg, 2 at push), 19 INERT (`stages: [manual]`)**, and four report-only conductor jobs (pytest, ruff, seal, commit-gate).
- **The live integrator order is not 14 -> 15 -> 16.** `/lane-integrate` runs, **per lane**, `git merge --no-ff` **locally first**, then `review_packet.py` on the merge, then the full suite and the review **concurrently** (`merge_receipt.py race`), then **teardown** of that lane's worktree and branch (lane-integrate.md :117-139); the **one** `git push` comes afterwards, in §3, after the whole walk (:386), and the Actions verdict of the pushed merge is read after that (`merge_receipt.py actions` prints `NO-RUN` for an unpushed SHA and a later row refuses the merge, :192-195). The file itself says **where the push sits relative to the per-lane block is UNRESOLVED and not a lane's to choose** (:204-217, `[#750]`). So review and gates run between a *local* merge and a push whose position the protocol has not settled: MERGE is two acts (merge, push) with 14 and 15 after the first. Stage 14 also occurs earlier, at the lane, as the HANDBACK `review=codex ...` tally the integrator only *reads*. R1's stage-15 list (audit / ship-gate / ruff / impacted tests) is also narrower than what the integrator gates on today (the full pytest suite once on the merged result, and the Actions verdict). As written, the review packet's `--range main..worktree-$L` is evaluated after that merge, when `main` already contains the lane tip — an empty range. **The ADR has to say where 14 and 15 sit relative to the local merge and the push.**
- **Missing, concretely:** (1) no `harness.yaml` row: nothing composes ship-gate + impacted tests + ruff into one verdict for a change; (2) a trigger — 19 hooks and the audit's 55 checks run only by hand or in report-only CI, so a spine stage 15 would be their first automatic run inside a work loop (whether that re-arms them is a decision, and it is the ADR's to record, not this lane's); (3) a verdict shape the merge stage can read (exit code today; `audit.py handback` reads a line, not a gate result).

**Stage 16 MERGE — the refusals exist; the GO is a spoken ceremony on the merge side.**
- Fills it today: `/lane-integrate` (its §0a-§4 walk; runs `audit.py handback` per item — "exit 0 merges, exit 1 refuses"), `/ship` (one branch), the two ARMED pre-push refusals `block_ff_push` and `block_unanchored_push` (`journal_anchor.py` is the predicate), `batch_manifest.py`, `merge_receipt.py`, `actions_verdict.py`, `id_allocator.py`, and PLAYBOOK Ch8 D0-D5 / teardown as prose.
- **Missing, concretely:** (1) **the merge-side GO artifact.** `lane_boot.py` already turns the operator's boot GO into a file it reads (a manifest row naming the lane whose `State` cell is not `HELD`, `[#685]` — the seat's roster state, not the operator's own ratification file, which its docstring records as a documented gap); `/lane-integrate` §0 still says "One operator GO authorizes the whole batch integration" as prose — no organ reads it.
