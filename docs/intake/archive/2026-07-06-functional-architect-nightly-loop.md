# INTAKE BRIEF — the functional-architect scene + the nightly proposal loop
Status: CONSUMED (ADR-98, #268) · Origin: operator voice session + architect synthesis, 2026-07-06
Meta: this document is itself the FIRST artifact of the process it proposes — file it as intake doc #1 and dogfood the triage on it.

## 1. Problem
The pipeline starts at the backlog; there is NO named stage for where requirements come from. Audits do double duty (evidence about state vs requests to change state) — different genres, one folder, which is part of "too many audits nobody reads". The operator's natural working mode is fluid voice conversation, and it has no capture format and no conversion path into structured requirements. Separately: nightly routines exist without consumers (automation/fleet-audit: 61 daily baselines, zero readers) — a routine without a consumer is a rot generator.

## 2. Proposed model — three chat roles, three handoff modes
- **Functional architect (NEW)** — a lightweight browser chat whose ONLY product is an intake document. Gathers requirements through fluid conversation (the operator talks, it structures). Does NOT write ADRs, does not touch the backlog, does not design solutions.
- **Technical architect (existing role, name it)** — consumes intake docs; owns ADRs, backlog structure, epic handoffs, UAT sign-off. Authors ADRs with intake docs (the "what/why") + audits (the "how it is") as inputs; the operator ratifies.
- **Epic lanes** — unchanged (§14).
- Handoff modes: `--mode architect` (technical; exists) · `--mode epic` (exists) · `--mode functional` (NEW, to build).
Corporate mapping the operator wants preserved (BY delivery + his thesis): blueprint = intake doc · implementation = epic lanes · UAT = acceptance criteria checked at EPIC RETURN · go-live = root merge + closure declaration. One thread: the intake doc's acceptance criteria ARE the UAT script.

## 3. The functional boot (what a fresh functional-architect chat receives)
Generated by CC from committed state (`gen_handoff --mode functional`), deliberately MINIMAL — the functional chat's subject is the operator's head, not the repo:
1. **Vision extract** — VISION.md core + a one-paragraph current-state summary (so the chat knows what the project is without the operator explaining).
2. **Role contract** — does/does-NOT list above, the output format (§4), the conversion path (§5), and the stance: listen, probe with scenario questions, structure — never solutionize.
3. **Intake index** — open/parked intake docs (so conversations don't re-discover) + parked idea seeds from the nightly loop (§6).
4. NO live-state probes (unlike architect/epic boots) — a state summary suffices; ground-truth verification is the technical architect's lane. If the conversation turns technical-factual, the functional chat says "that's a technical-architect question" and records it as an open question instead of guessing.
Opening move after boot: "Here's where the project stands. What are we exploring?" — then the operator talks.

## 4. Intake document format (the artifact)
Home: `intake/` (operator-chosen name — the operator considered discovery/ and reverted to intake/ on 2026-07-06; NEW top-level folder, needs the standing folder-approval at build time). Framed on the operator's own thesis method — 4+1, where the +1 scenarios view drives the rest:
- **Problem / motivation** — why now, in one paragraph.
- **Scenarios (+1 view)** — concrete walkthroughs: "as the operator I … and then …". The load-bearing section; requirements without a scenario are suspect.
- **Functional requirements** — must / should / could (keep it this simple unless build-time review prefers MoSCoW).
- **Acceptance criteria (ex-ante)** — measurable; these become the UAT script at EPIC RETURN, verbatim.
- **Non-goals** — what this explicitly does not cover.
- **Impact sketch (4+1 lite)** — one line per view: logical / process / development / physical — which views does this touch? (Keeps the thesis framing honest without ceremony.)
- **Open questions** — including everything the functional chat refused to guess.
- **Status**: DRAFT → READY-FOR-TECHNICAL → CONSUMED (backlog/ADR ids) | REJECTED (with the one-line why, kept — rejections are knowledge).
Conversion path for fluid sessions: voice/chat ramble → CC converts the transcript or the architect's synthesis into this format → operator approves the draft → lands in `intake/`.

## 5. Lifecycle (the closed loop)
functional chat (fluid) → intake doc (CC-formatted, operator-approved) → technical-architect TRIAGE: accept (→ ADR and/or backlog epic; doc status CONSUMED with ids) / defer (parked, visible in the index) / reject (recorded) → epic handoff → build → UAT against the doc's acceptance criteria at EPIC RETURN → operator sign-off → closure. What does NOT change: the core loop, §14 mechanics, ADR authorship (technical authors, operator ratifies), closure discipline, the handoff machinery.

## 6. Nightly proposal loop (rulings from this session — carried as constraints, not suggestions)
Governing rule: **every routine names its CONSUMER + a survival metric ex-ante** (the fleet-audit lesson). Load-gauge lands FIRST (standing operator ruling: before more mechanisms).
- **Execute at night (safe, deterministic):** full serial test suite + a timing-trend report (Epic-5 nightly path — wire it, it exists); deterministic hygiene limited to mechanically-verifiable classes (format, import sort, `--fix`-able lints); rot-report run once built (Phase-2 is unlocked — do NOT build a separate audit routine; rot-report IS the nightly audit).
- **Propose-only at night (never mutate):** refactor candidates (complexity/dead-code flags — flagged, not deleted); ADR drafts (status Proposed); functional feature ideas → `intake/` as status=SEED (no separate proposals/ folder — avoid folder proliferation).
- **Morning triage** by the technical architect, with two teeth: CAP — max ~5 proposals/night, untriaged items auto-expire in 7 days (else morning review becomes new toil = fleet-audit 2.0); SURVIVAL METRIC — accept-rate under ~20% after 2 weeks kills the routine. Routines pay rent.
- **Hard boundary (proven doctrine, overnight experiment):** no autonomous semantic refactoring at night — night executes pre-authorized contracts; judgment sleeps with the architect.
