# ADR-37 — Session Boundary Protocol (two-phase handoff format)

<!-- scope: meta -->

Status: Accepted
Date: 2026-04-30
Augments: ADR-32 (HANDOFF_PROCESS v2.0)
Related: ADR-29 (grandfathering pattern), ADR-33 (universalization),
         ADR-36 (audit tool — STRONG mandate consumer),
         ADR-38 (Cross-Session Backlog Architecture, pending),
         transcript council-out-20260430-132308-*

## Context

Existing handoff format (ADR-32 v2.0, 9-section structure) is
dominantly backward-looking: what was done, decisions made, files
modified, pending list. Forward-looking content is implicit in
"Pending — next session candidates" but not framed as authoritative
guidance to the incoming session.

Two-phase framing makes this explicit: each handoff has a Current
State (where the project is) and a Future State (where it's going).
Forward-looking content becomes a first-class artifact, not a
trailing list.

This is cross-cutting: affects session handoffs, audit handoffs
(ADR-36 consumer), and future cross-repo handoffs (Phase 2
universalization).

Council debate (council-out-20260430-132308-*) covered Q1-Q7.

## Decision

### Structure (Q1 + Q3) — Augment, not supersede

HANDOFF.md gains TWO top-level sections at the start:
- `## Current State`
- `## Future State`

ADR-32 9-section structure remains beneath, under header:
- `## Detailed Context`

(NOT "Archival Context" — those sections are reference/workshop floor,
not historical museum.)

Canonicality:
- **Top-level Current/Future State** = AUTHORITATIVE operational state
- **Detailed Context (9 sections)** = REFERENCE evidence and history

If contradiction between top-level summary and detailed sections,
top-level wins as operational source of truth.

### Per-phase content (Q2)

**Current State** contains:
- Verified factual status (compliance, build, tests, branch state)
- High-level summary of decisions made this session
- Open questions / unresolved items
- Last verified commit SHA + timestamp

**Future State** contains:
- Next session goal (1-3 session horizon, NOT multi-quarter)
- Recommended actions in priority order
- Dependencies between actions
- Reference to BACKLOG.md items (per ADR-38, when ratified)

### Mandate strength (Q6) — Type-dependent

**AUDIT handoffs** (machine-generated by audit tool per ADR-36):
- STRONG mandate
- Validator rejects handoff folder if Future State missing
- Acceptable because deterministic generation

**SESSION handoffs** (human-curated by departing browser chat):
- MEDIUM mandate
- Future State must be present, but MAY explicitly state:
  `Future state: undetermined — [justification]`
- Justification required (per Rob's "Defer requires justification"):
  - cognitive exhaustion (end-of-session fatigue)
  - scope mismatch (ran out of architectural context)
  - dependency unresolved (waiting for external input)
- "Future state: undetermined" without justification = invalid

### Drift mitigation (Q5) — Two layers

Layer 1 (primary): **Browser 2 mandatory validation step before action**
- Read Current State first
- Validate Future State against current git HEAD and project reality
- Log reconciliation note before acting

Layer 2: **Browser 1 instrumentation for trivial drift detection**
- Future State header includes timestamp + commit SHA
- Browser 2 compares current HEAD vs handoff SHA → drift signal

Confidence level (per-section h/m/l) considered and DROPPED — without
enforcement mechanism = decoration. May be added in future amendment
if usage data shows need.

### Validation enforcement (Rob's pushback)

Validation instruction lives in `first-message.md` template
(template-level enforcement), NOT system prompt modification.

- Audit handoffs `first-message.md`: STRONG ("MUST validate before acting")
- Session handoffs `first-message.md`: MEDIUM ("SHOULD validate before acting")

Implementation deferred to ADR-32 update session — `HANDOFF_PROCESS.md`
+ `HANDOFF_TEMPLATE.md` will be updated to reflect ADR-37 overlay.

### Horizon definition (Q4)

- **Future State** = 1-3 session tactical horizon
- **VISION.md** = quarter+ strategic horizon
- Future State MAY reference VISION sections if directly relevant
- Linking VISION NOT mandatory
- No conflict resolution needed — different layers

### Implementation phasing (Q7) — Forward-only

- ADR-37 effective immediately for new handoffs from ratification date
- Existing handoff folders grandfathered (per ADR-29 pattern):
  all handoffs created before 2026-04-30 are valid in original format
- HANDOFF_PROCESS.md update — separate session
- HANDOFF_TEMPLATE.md update — separate session
- Audit pipeline integration (ADR-36) — separate session

### Universalization (per ADR-33 pattern)

- **Mandate**: .dev-knowledge handoffs
- **Recommendation**: child repos with handoff workflows
- **Cross-repo audit (Phase 3)**: auditor verifies handoff format
  compliance per repo

## Consequences

### Positive
- Universal forward-looking pattern across handoff types
- Clear canonicality (top-level operational, detailed reference)
- Type-dependent mandate respects human cognitive limits
- Two-tier drift mitigation (validation + instrumentation)
- Explicit horizon prevents VISION/handoff overlap
- Solo dev with LLM-driven workflow gets explicit forward-looking
  artifact without Scrum ceremony tax (per ADR-38 framework)

### Negative
- Slight increase in handoff length (+10-15 lines for top-level sections)
- Existing handoff template needs update (separate session)
- Browser 2 validation is honor-system in markdown — first-message.md
  template is the practical boundary
- Dual-maintenance drift risk between top-level summary and detailed
  sections (mitigated by canonicality rule: top-level wins)

### Follow-ups
- HANDOFF_PROCESS.md update reflecting two-phase overlay (separate session)
- HANDOFF_TEMPLATE.md restructure (separate session)
- ADR-38 ratification — defines where Future State pending items persist
- Audit pipeline (ADR-36) integration: validator hooks for STRONG mandate
- 6-month review: measure whether Future State sections are used or skipped
