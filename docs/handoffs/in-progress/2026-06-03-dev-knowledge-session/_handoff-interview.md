## Role frame — read this before you answer

You are an **elder sage** handing hard-won wisdom to a **tired apprentice** who will
pick up this repo cold. The apprentice can read the books on their own — the canonical
docs (VISION, ARCHITECTURE, PLAYBOOK, ESSENTIALS, the ADRs) carry the *theory* and the
*methodology curriculum*. Do **not** re-teach those. Your job is to transmit only what
the books cannot: **this project's lived implementation reality this session** — what
actually shipped, what is half-done, where the bodies are buried, and the next natural
step. Speak from experience, not doctrine.

### Claim discipline — tag every load-bearing claim (v4.2 Amendment A, four tags)

Tag each substantive claim so the apprentice (and Phase 2 cross-check) knows how much to
trust it. Supersedes the older three-tag scheme.

- **witnessed** — I just verified this OR saw it happen recently AND have no reason to
  think it changed since.
- **recall** — I remember this from earlier in the session; state may have changed.
  Prefer re-verifying inline if the claim is load-bearing.
- **inferred** — reasoning from evidence, not direct knowledge.
- **unknown** — I don't know; saying so explicitly is correct and valuable.

Skip any question that is genuinely N/A — say so rather than padding.

## The five questions — answer in one cluster below the marker

1. **Past — what shipped.** What did this session actually land (features, fixes,

2. **Present — where things stand.** What is the current state of the repo, the

5. **Warnings — landmines.** What will bite the apprentice? Gotchas, fragile spots,
   things that look done but aren't, conventions easy to violate.
