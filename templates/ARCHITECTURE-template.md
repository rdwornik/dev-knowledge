## Applicability & conventions

**This template is the single canonical `ARCHITECTURE.md` for the `.dev-knowledge` ecosystem.** It is mandated by ADR-51 and inherited unchanged by every repo that adopts it. There are no per-repo template variants.

**Coverage (universal — tier system deprecated 2026-05-23):** `ARCHITECTURE.md` at repo root is **mandatory for every repo**, regardless of size (ADR-51 amendment 2026-05-23; ADR-38 amendment A5; root placement per ADR-38 A3). The prior S-exempt / M+L-mandatory split is withdrawn.

**Required content:** every `ARCHITECTURE.md` completes the **CORE** sections (`Purpose`, `Codemap`, `Layer Boundaries & Invariants`). The remaining sections are completed as the repo's complexity warrants. The codemap is **generated compact text** (canonical docs are LLM-first — no Mermaid; ADR-51 amendment 2026-07-05); a repo too small for a meaningful package graph MAY use a hand-written prose module overview instead (operator judgment — see the codemap note below), no longer tier-determined.

**Section tags:** only `[CORE]` is used — it marks the three sections every `ARCHITECTURE.md` must complete (Purpose, Codemap, Layer Boundaries & Invariants). All other sections carry no tag; complete or delete them by judgment of what the repo needs.

**Pointer convention (doc-wide).** Cross-references to other artifacts use a single line: `→ <description>: `<relative/path>`` (arrow + colon, backticked path). Used in §3 and §11 below as well as §4 Diagrams.

**Governing conventions** (these live in the `.dev-knowledge` ecosystem repo, not in this repo): ADR-51 (architecture doc convention, including amendment 2026-05-22 — codemap generator output specification — and amendment 2026-07-05 — LLM-first canonical docs, compact-text codemap form), ADR-38 (universal repo baseline; root-placement amendment A3), ADR-36 (read-only audit contract).

## Codemap [CORE]

The codemap is the canonical artifact answering *"what exists and how does it relate?"*. ADR-51 amendment 2026-05-22 (generator + markers + freshness gate) as re-formed by amendment 2026-07-05 (LLM-first: compact text, no Mermaid) specifies its form:

- **Default — generated compact text**: an auto-generated module/layer table + dependency list between `<!-- CODEMAP:START -->` and `<!-- CODEMAP:END -->` markers, carrying modules, `tach.toml` layer assignments, import edges, orphan/cycle flags, and per-module source paths. Generated by `python -m scripts.codemap.cli generate . --write` (see `protocols/PLAYBOOK.md` § Codemap workflow); **hand-authoring the block is refused** (derive-don't-maintain). A pre-commit freshness hook (`codemap check`) blocks commits if this block drifts from the current source state.
- **Prose override**: a repo too small for a meaningful package graph MAY use a hand-written prose module overview (no generator dependency). Operator judgment, no longer tier-gated. See the prose-override note below.

The narrative invariants in §3 are **not** generated — only the codemap is. Human-facing diagrams (system context, pipeline, data flow) are a separate visualization surface documented in §4 Diagrams (ADR-51 amendment 2026-07-05 Decision 3); they complement but never replace the codemap and never live inline in canonical docs.

## Diagrams

Additional C4-style diagrams that surround the codemap — the **human-facing visualization surface** (ADR-51 amendment 2026-07-05 Decision 3). The §2 codemap is the canonical *modules-and-relations* artifact (generated compact text); the diagrams here are the supporting cast — system context, pipeline / data flow, and any other orientation aids the repo needs. They **complement** the codemap, not replace it, and they live under `docs/diagrams/` — **never inline in canonical docs**.

**Source format:** Mermaid (`.mermaid` files under `docs/diagrams/`). The ADR-51 v2 high-contrast theme standard applies here as guidance (re-scoped from canonical docs by the 2026-07-05 amendment; not audit-enforced).
**Render pipeline:** Mermaid source → SVG. Any Mermaid-to-SVG renderer is acceptable (e.g., `mmdc` via npm); the specific tool is a repo-level choice and lives in a render script under `scripts/` or a CI job. **No specific tool is mandated by this template.**
**Output location:** SVGs co-located with their `.mermaid` sources (`docs/diagrams/*.svg`).
**Freshness check intent:** the CI codemap freshness check should be extended (or paired with a separate hook) to detect `.mermaid` sources that have changed without a corresponding SVG regeneration. Pending implementation — tracked alongside the codemap generator open item.

**Recommended diagram set (add or omit as the repo needs):**

| Diagram | Source | Output | Inline reference |
|---------|--------|--------|------------------|
| System context (C4 L1) | `docs/diagrams/system-context.mermaid` | `docs/diagrams/system-context.svg` | placed at the end of §1 Purpose |
| Pipeline / data flow | `docs/diagrams/pipeline.mermaid` | `docs/diagrams/pipeline.svg` | placed at the end of §6 Data Flow |
| Other repo-specific views | `docs/diagrams/<name>.mermaid` | `docs/diagrams/<name>.svg` | inline at the relevant section |

> The **module-map / codemap** is **not** listed here — it lives in §2 Codemap (the canonical generated compact-text codemap). Adding a "module map" diagram in this section creates two competing maps that drift independently.

**Inline reference format:** at the end of each relevant section, add one line — `→ <diagram name>: `docs/diagrams/<file>.svg``. Per the pointer convention defined in the header.
