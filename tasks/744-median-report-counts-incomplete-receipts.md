- [#744] [P1][S] **`median_report` filters receipts by kind but never by completeness, so the under-30 target can be met on incomplete receipts** - Operator ratification 2026-09-13 item 3 (`to-browser/RATIFICATION-2026-09-13.md`), which held `[#675]` open as NO-GO and ruled its three verified false-pass holes into rows. This is the third. · **The defect, resolved in the code:** `scripts/merge_receipt.py:448-457` selects `wanted = [r for r in receipts if r.kind == kind]` and computes the median over `r.wall_seconds()` for each. **`kind` is the only filter.** `Receipt.closed` is declared `Optional[str] = None` (line 176), so a receipt abandoned mid-merge — the integrator interrupted, the session ended, a step raised — is a valid `Receipt` carrying only the steps that completed, and `wall_seconds()` happily totals those few. It is counted. · **The bias runs the wrong way, which is what makes it a false pass rather than noise.** An abandoned merge has FEWER recorded steps, so it reports a SHORTER wall time, so it pulls the median DOWN — toward the very threshold the target is measured against. `[#675]`'s target 6 asks for "median merge under 30 minutes, MEASURED", and the row's own text calls a median reached by cutting the work "a false pass on this row". A median reached by counting merges that were never finished is the same false pass arrived at by an even cheaper route: **the measurement improves precisely when the process fails.** · **The docstring shows the author already reasoned about exactly this and stopped one predicate short.** It says filtering by kind "is not a convenience... a ledger that also holds lane commit arcs would answer a cheaper question under the same name" — the correct instinct, applied to kind and not to completeness. A ledger that also holds ABANDONED merges answers a cheaper question under the same name, by the identical argument. · **`median --strict` does not currently rescue it** — per the wave-2 review the strict path still counts closed receipts with missing or failed steps, so "strict" narrows the wrong axis. Whether the fix belongs in `median_report` (exclude), in `--strict` (define it as complete-only) or in both is the implementer's call, but a mode named strict that admits an incomplete receipt is itself part of the defect. · Done when: a receipt that is not complete is EXCLUDED from the median — with "complete" given one explicit predicate in code (at minimum `closed is not None` plus every declared step present and non-failed) rather than left to the reader; the exclusion is REPORTED alongside the median the same way `excluded` already reports the kind filter, so a median over a thinned sample never renders as a median over a full one; **one test FAILS before the fix** — a RED-first witness per ADR-108 §B building a ledger of complete receipts above the threshold plus incomplete ones below it, asserting the median is computed on the complete set only and is NOT under the target, still RED if completeness filtering is later dropped; and `median --strict` either enforces completeness or is documented as not being the completeness axis, with a test pinning whichever is chosen · **Done-when authored by the integrator seat** from the ratification's item 3 and the code read at `scripts/merge_receipt.py:167-200, 448-462` · refs `scripts/merge_receipt.py` (line 176 `closed: Optional[str] = None`;
