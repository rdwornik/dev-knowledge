- [#783] [P2][S] **The carried-to-RESOLVED leg of decision-coverage has never once been exercised** - `decision_coverage.py` gives a transport decision exactly two ways out: an OPEN row whose body carries an implements clause naming the decision, or the doc itself carrying a `resolves:` line (`gen_handoff.CARRIAGE_RESOLVES`). **Measured 2026-09-15: zero documents in `CLAUDE_PROMPTS_DIR/to-cc/` carry a `resolves:` line** -- every one stops at `carried-by:`. One of the two legs has never been exercised, so the whole population is forced down the other. **The asymmetry is the bug:** `carried-by:` marks a doc as having a carrier, `resolves:` marks it discharged, and nothing in the process ever performs the second write -- the carrier lands and the decision stays unresolved forever, which is why `[#764]` had to be filed at all. **Recorded because the dispatcher got it wrong first:** the row-path is NOT one row per decision -- `gen_task_tree._IMPLEMENTS_RE` reads a COMMA-SEPARATED LIST from one dedicated clause, so a single row resolves all four, which is what `[#764]` does. A first pass at this row asserted the opposite and filed two rows that were not needed; they were withdrawn before landing. The live defect is the dead `resolves:` leg, not the row path. - Done when: either the `carried-by:` -> `resolves:` write is performed by the organ that lands a carrier (so a decision discharges when its carrier commits, needing no row), or the `resolves:` leg is removed and `decision_coverage` says plainly that a row is the only path -- the one outcome that is NOT acceptable is leaving a specified leg nothing has ever exercised, because that is a mechanism which reads as enforcement and is decoration - refs `scripts/decision_coverage.py` (the two legs), `scripts/gen_handoff.py::CARRIAGE_RESOLVES` (the token), `scripts/gen_task_tree.py::_IMPLEMENTS_RE` (the comma-separated list this row got wrong first), `[#764]` (the row that resolved all four decisions the engine refused, and which asks the adjacent disposition question), `docs/audits/2026-09-15-technical-batch-z-manifest.md`, ADR-119 - kill-candidates: none -- `[#692]` built decision-coverage and is CLOSED; `[#764]` discharges tonight's four decisions and asks whether a SUPERSEDED decision should resolve by disposition, which is adjacent to but not the same as this row's finding that the `resolves:` leg is dead for ALL decisions, superseded or not - source: batch Z, dispatcher seat, found while landing the batch manifest
