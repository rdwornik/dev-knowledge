- [#767] [P2][M] **A tool description is gated only where it is generated, and no surface gates its parameters at all** -- AJ M04 states the requirement as two things, not one: *"przy definicji narzędzia bardzo ważne są dwie rzeczy. Oczywiście to jest opis schematu wejściowego, wyjściowego danego narzędzia, ale też opis tego narzędzia"* (`AJ_M04_transkrypcje.md:153-154`) -- a description of the INPUT/OUTPUT SCHEMA **and** a description of the tool. L06 repeats the schema half as an obligation -- *"musi być bardzo dokładnie opisane, żeby LLM wiedział, jakich informacji się spodziewać"* (`1053-1055`) -- and L05 extends it to state parameters: *"warto zadbać o odpowiednie nazewnictwo i opis tych parametrów, żeby model nie miał wątpliwości"* (`949-952`). All three verified against the source. · **The tool half is gated for exactly one population.** `[#728]` requires that every question-answering organ's skill be RENDERED from `ecosystem/organ-index.md` with a description stating WHEN to invoke it -- *"the situation, not the organ's name"* -- plus a freshness gate refusing a hand-edited generated skill. That is the right rule and it binds only the generated set. · **The hand-authored population is ungated and it is the one a session actually reads.** `.claude/commands/*.md` frontmatter descriptions are hand-written; `gen_claude_rosters.py` renders them VERBATIM into `.claude/generated/commands-repo.md` and the `claude-rosters-freshness` hook checks only that the rendering is FRESH -- never what the description says. A command whose description names the organ rather than the situation regenerates cleanly and passes every gate. · **The parameter half is ungated everywhere.** No surface in this repo describes a command's or a skill's arguments at all: not the frontmatter schema, not the roster generators, not `validate_hermetization`. `/handoff`, `/lane-boot` and `/preflight` all take arguments and none is described anywhere a model reads. · **ADR-119 measures the outcome and cannot govern the input.** It rules that a command file counts as a wiring surface only while invocations are recorded -- adoption decays. That correctly detects a command nobody invokes and says nothing about WHY, and a description that does not say when to invoke it is the most likely why. · Done when: a checkable predicate applies to EVERY command and skill description this repo ships, generated and hand-authored alike -- at minimum that it states an invocation SITUATION rather than restating the organ's name -- and every command or skill taking arguments describes them in a surface a model reads, with the gate naming the offending file rather than reporting a count · refs `AJ_M04_transkrypcje.md:153-154, 949-952, 1053-1055` (the three obligations, quoted above), `docs/audits/2026-09-15-technical-lane-z-10-aj-m04-evidence/LOCATOR-VERIFICATION.md` (items 05, 66, 70 -- verified), `[#728]` (the generated half, which this row extends rather than restates), `scripts/gen_claude_rosters.py` (renders hand-authored descriptions verbatim), `.claude/generated/commands-repo.md` (the rendered surface), ADR-119 (`c8058953`, measures adoption without governing the description) · kill-candidates: none -- `[#728]` owns the GENERATION of organ skills from the index and would be satisfied without touching a single hand-authored command description, which is the population this row is about; ADR-119 owns decay of a wiring claim and detects the symptom rather than the cause · source: batch Z lane z-10, AJ M04 first pass, `[#784]`
