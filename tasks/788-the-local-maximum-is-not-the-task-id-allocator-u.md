- [#788] [P1][M] **The local maximum is not the task-id allocator under concurrency -- a sibling branch's held id is invisible from a worktree and nothing in the repo refuses it** - **The measured instance, 2026-09-15, and it was caught by luck rather than by a gate.** The codespaces-platform-conformance lane needed a new row. It scanned `tasks/*.md`, `tasks/archive/*.md` and every `[#id]` reference in the tree, found 785 as the highest, and allocated **786**. 786 was already held by lane **aa-4's branch** -- a branch that had not pushed, so it appears in no local ref, no `git ls-remote`, no `tasks/manifest.json` and no `BACKLOG.md`. **Every id surface in the repository agreed on an answer that was wrong.** The collision was caught only because the lane happened to open `LANE-aa-14-resource-lifecycle.md` for an unrelated reason and read its tail: "Next free task id is 787 (785 is main's highest; 786 is held by lane aa-4's branch)." · **The allocator is in the operator's prompts directory, and the repo does not know that.** Three sibling contracts carry the statement -- aa-12 and aa-13 say "Task ids 786 and below are taken", aa-14 names 787 -- so the authority is real, it is maintained, and it is OUTSIDE the tree every automated check reads. A lane that never opens a sibling's contract has no path to it. · **This is not the same defect as the one already recorded.** The known trap is that a seat allocating an id while its OWN lanes run can collide with itself; that is about timing and is mitigated by re-checking. This one is about VISIBILITY and re-checking does not touch it: the held id is unobservable from the tree at every instant, before and after, so a re-check returns the same wrong answer with more confidence. · **What makes it dangerous rather than annoying.** `gen_task_tree` DOES refuse a duplicate id -- "an id is allocated once (ADR-107 6.3; the concurrent-branch collision this gate exists to catch)" -- but only once both files are in ONE tree, which is at integration, after both lanes have built on their ids: the row file, the manifest node, the commit messages, any cross-refs, and the branch name. The gate is real and it fires at the most expensive possible moment. Filing is cheap; renumbering after a lane has cited its own id is not. · **Shape of the fix is deliberately open, and one candidate is named only to be argued with.** A `next-free-id` verb that reads the prompts directory would put an operator-disk path inside a hub organ, which cuts against ADR-28's layering; a reservation file inside the repo would be a second authority competing with the contracts; pushing the branch at allocation makes the id visible but forces a push before there is anything to push. The right answer may be that the contracts stay the allocator and the LANE PROTOCOL names reading them as a step -- a convention with a checkable artifact, not a gate. Deciding that is the work. · Done when: the allocation authority is named in one place a lane is required to read before filing, and that requirement lives in the lane protocol rather than in a contract's tail where only the lanes that happen to open it will see it; and either a checkable surface exists that can refuse an id held outside the tree, or a recorded decision states that no such surface can exist within ADR-28's layering and names the convention that replaces it -- an honest "convention, not gate" closes this row, and a gate that can only see the local tree does not, because that is the gate we already have · refs `scripts/gen_task_tree.py` (the duplicate-id refusal at integration, ADR-107 6.3), `tasks/manifest.json` (a surface that cannot see an unpushed sibling), `protocols/PLAYBOOK.md` Ch8 (lane boundaries, where the read-the-allocator step would live), `[#787]` (filed in the same arc and renumbered by this very defect), `[#697]` · kill-candidates: none -- `[#787]` stays open because it owns test double fidelity and this row owns id allocation, two unrelated mechanisms that share only the arc that found them; no existing row covers allocation visibility across branches
