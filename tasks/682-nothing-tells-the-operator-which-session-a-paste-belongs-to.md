- [#682] [P2][S] **Nothing tells the operator which session a paste belongs to, so a correct paste delivered to the wrong seat is indistinguishable from a correct act** - **The one genuinely absent interface behaviour of the seven the 2026-09-10 architect supplement filed; the other six were struck as already documented.** The supplement names it `named-session addressing`: *"the browser tells the operator WHICH session a paste goes to (integrator · dispatcher · working CC · win-tooling · night), because Cloud SDK shows many concurrent sessions. Getting this wrong cost turns."* It was relied on throughout the window and `protocols/OPERATOR-INTERFACE.md` does not name it. · **The near-miss that makes this worth stating precisely**, recorded so the row is not closed by citing it: `OPERATOR-INTERFACE.md:83` says *"A chat paste is not addressable"*, and `:70` puts `owner-role: filings|dispatcher|integrator` in the inbox item's frontmatter. Those are a different claim - they make the **work** addressable by moving ownership into the file, which is why the transport v2 schema exists. Neither tells the operator, holding a block of text in front of N concurrent sessions, **which window to paste it into**. Reading `:83` as coverage would strike a real absence on a near-miss, which is exactly the error this row exists to record. · **Why it costs more than a lost turn.** A paste delivered to the wrong seat does not fail loudly: the receiving session boots, reads a contract that is not its own, and produces plausible work against the wrong scope. The failure surfaces later as a merge conflict, a doubled filing, or an act attributed to a seat that never ran it - the same detection profile the transport v2 `files:` clause was written to remove one layer down, and for the same reason. · **Not absorbed by the adjacent surfaces:** section 3 ("Every session ships its exact start command") makes a session **startable** and says nothing about which of several running sessions an already-started paste belongs to; `[#680]` owns the generator's unclaimed output; `[#681]` owns two documented-but-wrong sites in the same file - this one is a plain absence. · Done when: `OPERATOR-INTERFACE.md` names session addressing as a contract - every operator-directed paste block carries the seat it is addressed to, in a fixed position and vocabulary drawn from the live seat roster rather than invented per act; **and the addressee is machine-placed rather than remembered** - the assembler and the seat-boot templates emit it, so a block without an addressee is visible as malformed; and **one test FAILS when an operator-directed block carries no addressee** - a RED-first witness per ADR-108 section B, proven to bite before the check makes it green · refs `protocols/OPERATOR-INTERFACE.md` (:70 `owner-role:`, :83 "a chat paste is not addressable", section 3 the start command, section 7 the copy-ready block), `docs/handoffs/2026-09-10-dev-knowledge-architect/SUPPLEMENT.md` (Q7, the surviving row and the transcription note), `templates/handoff/seats/`, `scripts/assemble_paste.py`, `[#681]`, ADR-108 · kill-candidates: none - `[#681]` is the other half of this file's defects and owns the two documented-but-wrong sites, not an absence; no open row names session addressing · source: filed 2026-09-10 by the window-close handoff seat, from the single Q7 interface behaviour that survived verification against the file it was filed against
