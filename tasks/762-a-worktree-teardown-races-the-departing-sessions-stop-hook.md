- [#762] [P2][S] **A worktree teardown races the departing session's Stop hook, which re-creates the tree being removed — and the no-leftovers check cannot see what it leaves** — measured by the integrator seat on 2026-09-14 tearing down `lane-y-751` seconds after that lane said it was standing down. · **What happened, in the order it happened.** `git worktree remove` failed with `Permission denied`; git's ADMINISTRATIVE ENTRY was removed anyway, the DIRECTORY was not. `git worktree list` then no longer showed the worktree, `test -d` said it existed, `git -C <wt> status --porcelain` read CLEAN, and `rmdir` refused with *Directory not empty*. `find <wt> -mindepth 1` found one file: `logs/2026-09/DETECTOR-ERROR-2026-09-14.md`, whose own text names the cause — *"The session-end detector did not run: BACKLOG.md not found at …/worktrees/lane-y-751-cost-in-money (repo root resolved to …/worktrees/lane-y-751-cost-in-money) — the detector was pointed at a tree that is not the host repo"*. · **THE TEARDOWN DID NOT FAIL TO DELETE A LEFTOVER; THE DEPARTING SESSION CREATED A NEW ONE AFTER THE DELETION.** `propose_closures.py` (the `tier1-lifecycle` plugin's `Stop` hook) resolved repo root to the lane worktree, found no `BACKLOG.md` because the teardown had just removed it, and wrote its error log there — **re-creating `logs/<YYYY-MM>/` inside the directory that had been emptied moments earlier.** A teardown and a departing Stop hook are not ordered against each other, and the hook wins. · **The leftover is INVISIBLE to the check that would catch it.** `.gitignore:35` carries `logs/*/DETECTOR-ERROR-*.md`, so `git status` reports the worktree clean while it is not empty. **Critical rule 9 requires the provision→cleanup round-trip to leave the tree identical and requires removal to be VERIFIED** — and the obvious verification (`git status`, or git's own `worktree list`) returns clean/absent on exactly this state. Only `find <path> -mindepth 1` sees it. · **A SECOND, INDEPENDENT LEG, measured on `lane-y-752` the same day: a LOCKED worktree defeats both removal verbs.** Lane worktrees are created `locked`; `git worktree remove` refuses one, and **`git worktree prune` SKIPS one too**, so a teardown that falls back to `rm -rf` leaves git still registering a directory that no longer exists, and `git branch -d` then refuses with *cannot delete branch … used by worktree at …*. The teardown must `git worktree unlock` FIRST; unlock → remove → prune → branch delete succeeded immediately where the same sequence without unlock had left two of four end-state checks failing. · **Third trap, and it is a scripting one worth stating because it changes what a failed teardown looks like:** `set -e` stops the script at the failed `worktree remove`, so the branch deletion that follows never runs — leaving the branch alive for a reason unrelated to the husk and making one failure look like two. Teardown scripts must be IDEMPOTENT and must check each end-state condition separately rather than chaining. · **What it cost here, so the impact is not theoretical.** `merge-y-751`'s `teardown` step recorded `ok` while the husk survived — a receipt step that says a thing was done when it was not — and the receipt is closed and `logs/MERGE-RECEIPTS.jsonl` is append-only, so that row cannot be corrected. The husk was cleared by hand only after reading the leftover file and finding this cause. · Done when: a lane teardown either runs only after the lane's session is PROVEN gone, or the `Stop` hook refuses to write into a tree it has just resolved as not the host repo (its own error text already detects that condition and writes anyway); the teardown path unlocks before `remove`/`prune`; and the no-leftovers verification uses a filesystem enumeration (`find <path> -mindepth 1`) rather than `git status` or `git worktree list`, so a gitignored leftover cannot read as clean · refs `scripts/propose_closures.py` (the Stop hook that writes the file), `.gitignore:35` (why it is invisible), `CLAUDE.md` §5 critical rule 9 (the no-leftovers invariant this defeats), `[#750]` (owns the receipt whose teardown step recorded a false `ok`), `[#752]` (the lane whose locked worktree exposed the second leg) · kill-candidates: none — no open row carries worktree teardown hygiene, and the rule it defeats is a CLAUDE.md invariant rather than a row · source: integrator seat, batch Y close
