- [#742] [P1][S] **`actions_verdict` reports PASS when the job details cannot be read, so an unreadable run is indistinguishable from a clean one** - Operator ratification 2026-09-13 item 3 (`to-browser/RATIFICATION-2026-09-13.md`), which held `[#675]` open as NO-GO and ruled its three verified false-pass holes into rows. This is the first. · **The defect, resolved in the code rather than carried on the review's word:** `scripts/actions_verdict.py:206-213` runs `gh run view <id> --json jobs` and, on ANY failure of that second call, assigns `match["jobs"] = []`. The `except` catches `OSError`, `subprocess.SubprocessError` and `json.JSONDecodeError`, and the non-zero-returncode branch does the same thing — so a timeout, a `gh` auth expiry, a rate-limit, a network fault and a genuinely job-less run all produce the identical empty list. `verdict_for` then computes `failing = set()` over that empty list and returns `STATE_PASS`. **A completed run whose job details could not be read reports PASS.** · **This is the seventh-instance class `[#675]` itself names — a check that passes because it cannot see its own case — but it is a DISTINCT defect from `[#675]`'s node-defaulting read**, and it is the more dangerous one: the defaulting read produces a wrong value, this produces a GREEN verdict on a gate. · **The blast radius is the batch apparatus itself.** This is the instrument wave-3 slot 1 used to prove conductor E (`docs/audits/2026-09-13-technical-lane-x-689-conductor-e-proof.md`), and `[#675]`'s own target 2 asks for "full suite and index regeneration on GitHub Actions, with the integrator READING the result -- not merely running there, because a green run nobody reads is not a gate". A green run the reader CANNOT read, reported as green, is the same failure one layer deeper. · **The unreadable case and the clean case are different states and must return different values.** A third state (`STATE_UNKNOWN` / re-raising `ActionsUnavailable`) is the shape; silently degrading to PASS is the one option the row refuses. Note that the FIRST `gh` call in the same function already raises `ActionsUnavailable` on both a non-zero exit and unreadable JSON — the module already knows how to say "I could not read this", and the second call simply does not use it. · Done when: an unreadable, timed-out, errored or non-zero-exit `gh run view --json jobs` no longer yields `STATE_PASS` — it surfaces as an explicit unavailable/unknown state distinct from both PASS and FAIL, propagated to every caller that renders a verdict; and **one test FAILS before the fix and passes after** — a RED-first witness per ADR-108 §B that stubs the job-details call into each failure mode (non-zero exit, `OSError`, `subprocess.TimeoutExpired`, malformed JSON) and asserts the verdict is NOT `STATE_PASS`, still RED if the empty-list degradation is later reintroduced; and the distinction between "no failing jobs" and "no readable jobs" is asserted by a test that passes a genuinely job-less run and gets a different answer than an unreadable one · **Done-when authored by the integrator seat** from the ratification's item 3 and the code read at `scripts/actions_verdict.py:206` · refs `scripts/actions_verdict.py` (lines 205-213, the `match["jobs"] = []` degradation;
