- [#678] [P2][M] **The memory index is rolled by a seat's judgment, not by a rule, and the directory it lives in has no undo** - **A seat asked to shrink an index will choose what to forget, and that choice is unreviewable, unlogged and irreversible.** Measured 2026-09-09: Claude Code's project memory index at `~/.claude/projects/C--Users-1028120-Documents-Dev--dev-knowledge/memory/MEMORY.md` had reached **25,222 bytes across 324 entries** - past the 24,576-byte budget this fleet already applies to boot-time index files (`tests/test_claude_md_byte_cap.py`) - and was rolled **by hand** to 13,928 bytes / 166 entries, with 158 entries relocated byte-for-byte into `MEMORY-archive-2026-09-09.md` beside it. **The roll was mechanical only because the operator specified the predicate** (14 days) instead of asking for a smaller file; asked the second way, a seat prunes what it judges unimportant, and the entries most likely to look unimportant are the hard-won ones nobody has needed *recently*. · **The absence of an undo is the multiplier, and it is measured, not assumed:** `~/.claude/.gitignore:5` excludes this memory tree, so the index is under **no version control at all** - a bad roll is not revertable, has no diff, and leaves no record that anything was dropped. · **The dating signal is itself half-broken:** of the 324 memory files, **236 carry a `modified:` frontmatter stamp and 88 do not**, so more than a quarter of the age decisions fall back to **filesystem mtime** - which a re-save for any unrelated reason resets, making an old memory look new and silently exempting it from every future roll. An age rule reading mtime is not deterministic across machines or restores. · Done when: the roll runs as a **hook**, not a seat instruction - entries whose memory file is older than a declared N-day line move to a dated archive beside the index, the index carries the pointer line, and the operation is a **relocation that can never delete**; and **one test FAILS when a roll loses or duplicates an entry** (index-count + archive-count == pre-roll count, entry text byte-identical) and **one FAILS when the index is over budget after a roll** - RED-first witnesses per ADR-108 section B, proven to bite before the hook makes them green; and every memory file carries a `modified:` stamp at write time so age is read from **content, not mtime**; and the memory tree's exclusion from version control is either lifted or recorded as a ruling with the no-undo consequence stated · refs `~/.claude/projects/C--Users-1028120-Documents-Dev--dev-knowledge/memory/` (`MEMORY.md`, `MEMORY-archive-2026-09-09.md`), `~/.claude/.gitignore:5`, `tests/test_claude_md_byte_cap.py` (the 24,576-byte precedent), ADR-108 (section B, RED-first) · kill-candidates: none - no open row owns the memory index; the CLAUDE.md byte cap is a repo-file gate on a tracked file and shares only the number, not the mechanism or the no-undo exposure · source: operator act 2026-09-09, from rolling the index by hand and recording that the 14-day line - not the size target - is what made the roll safe
