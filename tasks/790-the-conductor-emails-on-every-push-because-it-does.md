- [#790] [P1][M] **The conductor emails on every push because it does not know about the frozen baseline — compare against the set, do not silence the notification** — operator direction, 2026-09-15. `main` carries a frozen baseline of **51** conductor failures and `.github/workflows/conductor.yml` knows nothing about the freeze, so every push produces a failure notification. **DO NOT SILENCE IT.** Silencing makes a real regression arrive as silence too, which converts a noisy-but-honest signal into a quiet-and-false one — strictly worse, and the failure mode the freeze file itself was written to prevent. · **THE RULE THE WORKFLOW MUST IMPLEMENT**, already stated in `logs/SUITE-BASELINE-FREEZE.md`: a failure **INSIDE** the frozen set is PRE-EXISTING and the job reports **success with the set named**; a failure **OUTSIDE** it is a **REGRESSION** and fails loudly. · **MEMBERSHIP IS BY TEST NODE ID, NOT BY COUNT — the freeze file is explicit and the distinction is load-bearing:** *"A file with 3 frozen members that fails 4 has a regression, and the count alone hides it."* A count-based comparison reproduces exactly the defect the freeze exists to prevent. · **THE WORKER COUNT IS NOT FIXED, contrary to the natural assumption.** The freeze file states in bold that the count is `auto`; it resolved to **4** (`gw0`–`gw3`) on a GitHub-hosted `ubuntu-latest` runner. *"A runner with a different core count re-partitions the suite and can flip cross-worker-sensitive members ... a comparison across different worker counts is not a like-for-like comparison."* **So the workflow must report its OWN resolved worker count and treat a mismatch as NOT-COMPARABLE rather than comparing across it.** · **THE BASELINE EXPIRES AT THE NEXT BATCH CLOSE, so the workflow must FAIL if the baseline file is MISSING or STALE rather than passing blind.** A comparison against an absent or expired baseline that reports success is a fail-open gate, and this repo has a standing count of those. The freeze records its measurement SHA (`b5270d63`), its source run (Actions `conductor` 34901604346, 2026-09-14T21:57:23Z) and its command — staleness is checkable against them. · **TWO MEASURED COMPLICATIONS the implementing lane must not discover late.** (1) The close packet records the baseline as **not fully reproducible** — *"the same tree measures 51 or 52"* — so an exact-set comparison needs a stated policy for the flapping member rather than treating it as a regression every other run. (2) Intake 100 records **five failures already sitting OUTSIDE the frozen 51**, so a naive implementation is RED on arrival; decide deliberately whether those five are the regression signal working correctly or evidence the baseline is already stale, and record which. · **RED-first:** a synthetic failure OUTSIDE the set must turn the job red, and one INSIDE it must not. Both legs, or the gate discriminates nothing. · Done when: the conductor compares by node id against `logs/SUITE-BASELINE-FREEZE.md`, reports success naming the pre-existing set, fails loudly on a member outside it, fails on a missing or stale baseline, records its own resolved worker count and refuses a cross-worker-count comparison; and both RED-first legs are witnessed · refs `logs/SUITE-BASELINE-FREEZE.md` (the set, its measurement conditions and its expiry rule), `.github/workflows/conductor.yml`, `docs/audits/2026-09-15-technical-batch-z-close-packet.md`, `[#724]` (the red-baseline epic this serves), `[#689]` (conductor E) · kill-candidates: none — `[#724]` owns fixing or dispositioning the members themselves, which is a different and larger act than making the signal readable while they exist · source: operator direction, dispatcher seat, 2026-09-15
