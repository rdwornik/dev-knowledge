- [#758] [P2][S] **`[#675]` target 3.2 has never been satisfiable by the `lane-integrate` walk** — target 3.2 asks for *"the integrator READING the result"* of a merge's suite run. The walk has read the Actions verdict **before the push** since before `[#750]`, and an unpushed merge commit does not exist on GitHub, so the read returns `NO-RUN` — unreadable, therefore INCOMPLETE, therefore refused. **The requirement has been structurally unreachable for its whole life and nothing reported it.** · **A · Why it stayed invisible, which is the part worth keeping.** Under the pre-`[#750]` code a `PRE-EXISTING` red arrived as `ok=False`, so every receipt was incomplete for a blanket reason and the specific impossibility was absorbed into it. **Fixing the completeness predicate is what made the ordering defect visible** — a gate becoming correct is what exposed it, not a new failure · **B · The two candidate topologies are not equivalent and the choice was made under constraint, not preference.** Push-per-merge keeps each receipt's span honest but requires a per-merge JOURNAL anchor, because `block_unanchored_push` carries **no exemption** (the ADR-110 declared-integration-arc exemption is the audit backstop's — that gate's own NOTE says so). A single end-of-batch push needs one anchor but produces **one Actions run, for the pushed tip only**, so every intermediate merge reads `NO-RUN` and is refused — it does not merely inflate wall time, **it makes per-merge verdicts structurally impossible**. Batch Y took push-per-merge with the anchor inside each merge commit, ratified 2026-09-14 as B8 · **C · What this row must decide rather than restate:** whether the walk's own text is the authority on ordering, or whether `require` should assert the precondition mechanically so a seat cannot run `actions` before a push and silently bank a `NO-RUN`.
