- [#787] [P2][M] **A test double for an external tool must CITE the real tool's contract for the behaviour it fakes -- a fixture nobody checked against the tool is a false-success surface** - **The measured instance, and it cost a month.** `Start-DispatchCodespace` carried several hundred lines of PowerShell that reconstructed a new codespace's name by diffing `gh codespace list` before and after the create, with a pre-create ambiguity probe, a post-create display-name refusal and a created-machine cleanup hanging off it. None of it was needed: `gh codespace create` PRINTS the name to stdout -- cli/cli, `pkg/cmd/codespace/create.go`, `fmt.Fprintln(a.io.Out, codespace.Name)`. The reason it was written is that FIVE fake `gh` doubles in `tests/test_dispatch_helpers_codespace.py` returned the literal string `created` from the create step. **The module was built to satisfy the fixture's world rather than the platform's**, the fixture's world was never checked against the tool, and every test passed the whole time. · **The class, which is why this is a row and not a changelog line.** A double that models a behaviour nobody verified against the real tool is the SAME defect class as a verb that reports success without effect -- the vacuous-gate family this repo already refuses in several other shapes. Both produce green that means nothing; both survive review because the thing that would contradict them is never consulted; and both get WORSE with test coverage, because each new test written against the double deepens the commitment to the fiction. A suite that is wrong about its dependency is not weakly tested, it is confidently wrong. · **The rule to enforce.** Where a test double stands in for an EXTERNAL tool (a CLI, an HTTP API, a platform SDK -- not an in-repo seam, whose contract is the repo's own and is already covered), the faked behaviour carries a citation to the real tool's contract: a documentation line, a source line, or a dated captured transcript of the tool actually being run. The citation sits AT the double, not in a packet, because the next author reads the fixture. · **What the fix already landed looks like, as the shape to generalise.** win-tooling `feat/codespace-name-from-stdout` replaced the five literals with one `CREATED_NAME` constant carrying the cli/cli source line that produces the value, in a comment at the constant. That is cheap, it is checkable by eye, and it makes the next hand-rolled invoker that drifts back a visible act rather than an invisible one. · **Scope honesty: the enforcing surface is NOT obvious and this row must not pretend otherwise.** A grep for doubles cannot tell an external-tool fake from an in-repo one, and a citation is prose that a regex can detect the PRESENCE of but never the TRUTH of -- so a naive gate would buy a second vacuous check, which is the very class this row exists to close. Deciding what can honestly be enforced (a convention with a reviewer prompt, a lint on a declared fixture registry, or a periodic audit) is part of the work, not a precondition to filing. · Done when: the rule is stated in the methodology where authors meet it rather than only in this row; the external-tool doubles in the fleet's existing suites are surveyed and each one either carries a contract citation or is recorded as an accepted gap with a reason; and the enforcement question is answered by a recorded decision that either names a live checkable surface or states, with its reasoning, that the rule stays a convention -- an honest "convention, not gate" closes this row and an invented gate that cannot detect a false citation does not · refs `tests/test_dispatch_helpers_codespace.py` (win-tooling, the measured instance and the `CREATED_NAME` fix), `config/dispatch-helpers/DispatchHelpers.psm1` (win-tooling, the ~300 lines the fixture caused), `[#697]` (the detached-lane zero-work row, whose investigation surfaced this), `ecosystem/quality-requirements.yaml` QR-AVAIL-009 (the identity requirement the same arc landed) · kill-candidates: none -- `[#697]` stays open because it owns a substrate MEASUREMENT and this row owns a TESTING DISCIPLINE, and closing either would leave the other's question unanswered; no existing row covers test double fidelity, which is why this one is filed rather than folded into one
