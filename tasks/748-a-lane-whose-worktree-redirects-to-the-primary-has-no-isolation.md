- [#748] [P1][M] **A lane whose worktree resolves to the primary checkout via a `core.worktree` redirect has no isolation, and dispatch cannot see it** - Witnessed live on 2026-09-13 by `lane-x-675-instrument-holes`, batch X4 slot 3 (`docs/audits/2026-09-13-technical-batch-x4-manifest.md` section 4.2). · **The defect:** a linked worktree's `.git` file points at `.git/worktrees/<name>/`, and a `core.worktree` value in that per-worktree config **redirects the working tree somewhere else**. When the redirect target is the primary checkout, every `git` question the lane asks is answered about the primary: `git rev-parse --show-toplevel`, `git status`, `git log`, `git branch --show-current`. **Nothing fails.** The lane believes it is isolated, its branch looks right, and its WRITES land in the integrator's tree. This is the same silent-resolution failure class as a torn-down worktree husk, but it is present from the moment of provisioning rather than arriving at teardown, so no amount of care by the lane can detect it. · **No organ anywhere reads `core.worktree`** - confirmed by grep across `scripts/`, `tests/`, `.pre-commit-config.yaml` and `.claude/`: zero hits outside `.venv`. `scripts/worktree_import_proof.py` is the closest existing organ and asks a genuinely different question (does THIS checkout's pytest import THIS checkout's source), it is wired into no gate, and an import proof passes cleanly on a redirected tree because the imports do resolve - to the primary. `scripts/audit.py::check_no_sibling_orphans` and `check_stale_worktrees` read `git worktree list --porcelain`, which reports the *registered* path and not the redirect. · **It has to fire at DISPATCH, not afterwards.** `[#675]` target 4 states the general principle for step-0 refusals and it binds here exactly: run after the session exists, the write the refusal exists to prevent has already landed in the primary, and every remaining option is a teardown plus a revert of whatever the lane touched. The check is cheap - resolve each provisioned worktree's top level and compare it to the primary root - and it is the only one of the family that can be answered before a session starts. · **Scope note for whoever takes this:** the refusal belongs on the `dispatcher` seat in `scripts/seat_refusals.py`, between `lane-ceiling` and `dryrun-step0`, and wiring it means four places plus a fifth - `REFUSALS`, `SEAT_REFUSALS`, the `refuse_*` function, the `@cli.command`, and `scripts/gen_seat_boot.py::_REFUSAL_LINES`, which `KeyError`s on an unknown id. The four roster meta-tests in `tests/test_seat_refusals.py` go RED until all five are done; that is the intended pressure, not a problem to route around. · Done when: a provisioned worktree whose resolved top level equals the primary checkout root is REFUSED at step 0 with the lane name and the redirect target both in the message; **the RED-first witness already exists and is the acceptance test** - `tests/test_dispatch_refusal_holes_x4.py::test_a_lane_whose_worktree_redirects_to_the_primary_is_REFUSED_before_launch`, currently `xfail(strict=True)`, so the implementing lane MUST remove the marker and a lane that implements the refusal without removing it goes RED on the XPASS; the check reads the resolved top level rather than `git worktree list`'s registered path, and a test asserts a *correctly* isolated worktree is NOT refused so the refusal cannot pass its own trip-test by refusing everything · **Filed by the integrator seat at batch X4 integration**, from the operator's instruction of 2026-09-13 · refs `scripts/seat_refusals.py` (`REFUSALS` line 81, `SEAT_REFUSALS` line 94, `_live_worktrees` line 639), `scripts/gen_seat_boot.py` (`_REFUSAL_LINES` line 109), `scripts/worktree_import_proof.py` (the adjacent, differently-scoped organ), `scripts/audit.py` (`check_no_sibling_orphans`, `check_stale_worktrees`), `tests/test_dispatch_refusal_holes_x4.py`, `docs/audits/2026-09-13-technical-batch-x4-manifest.md` (section 4.2, the witness), `[#675]` (target 4 - step-0 refusals fire before the cost is paid), `[#749]` (the sibling refusal from the same batch), ADR-108 (section B, RED-first), ADR-110 (the lane apparatus) · kill-candidates: none -- `[#675]` owns the instrument-hole programme and stays open as a sibling rather than a parent; no open row owns worktree isolation at dispatch time · source: operator instruction 2026-09-13, witnessed by lane-x-675-instrument-holes in batch X4
